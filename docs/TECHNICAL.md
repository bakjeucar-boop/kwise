# kWise 기술서

건물 전력 비용 진단·개선안 비교 도구. **개발자와 1년 뒤의 본인**이 읽는다.

이 문서는 **왜 그렇게 만들었는가**를 남긴다. 무엇을 하는지는 코드가 말하고,
어떻게 쓰는지는 매뉴얼이 말한다. 코드가 바뀔 때 갱신한다.

| | |
|---|---|
| 사용법 | `MANUAL.html` — 화면 조작과 결과 읽는 법 |
| 요구사항 | `REQUIREMENTS_kwise.md` — 무엇을 만들기로 했는가 |
| 진행 이력 | `PROCEED.md` — 세션별 기록과 결정 사항 |
| 근거 조문 | 이 문서 [부록 C](#부록-c-근거-조문-색인) — **한 곳에 모았다** |

## 1. 개요와 시스템 환경 {#tech-overview}

### 1.1 개발 배경과 목적 {#tech-purpose}

한전 15분 실측 사용량으로 **전력 비용 구조를 진단하고 개선 수단을 비교한다.**

처음 이름은 `peakcut` 이었고 태양광 피크 저감이 주인공이었다. 샘플 데이터를
돌려 보고 방향을 바꿨다 — **설비 투자 없이 선택요금 전환만으로 연 5,358만원**이
나왔다. 태양광부터 묻는 구조는 이 값을 가린다.

| | 이전 | 현재 |
|---|---|---|
| 목적 | 태양광 도입 시 절감액 산출 | 비용 구조 진단 + 개선 수단 비교 |
| 태양광 | 주인공 | 개선 수단 중 하나 (7.5) |
| 첫 산출물 | PV 피크 저감량 | **투자 없이 가능한 절감액** |
| 화면 | 업로드 → PV 입력 → 결과 | 1 진단 → 2 수단 → 3 비교 |

**설계를 관통하는 원칙 셋.**

1. **모르는 것은 모른다고 표시한다.** 금액을 지어내지 않는다. 단가를 넣지
   않으면 투자비는 0원이 아니라 `None` 이고 사유가 붙는다.
2. **코드에 기본값을 두지 않는다.** 법령 유래 수치와 판단값은 파일에 있다.
   코드에 남기면 파일을 고쳐도 반영되지 않고, 값이 그럴듯해서 결과를 다 쓰고
   나서야 발견된다.
3. **조용히 빼지 않는다.** 검토하지 않은 수단은 "효과 없음"이 아니라
   "미검토"로 적는다.

### 1.4 용어와 약어 {#tech-glossary}

**이 절이 나머지를 짧게 만든다.** 도메인 용어를 여기서 한 번만 정의한다.

| 용어 | 뜻 |
|---|---|
| **요금적용전력** | 기본요금을 매기는 kW. 관측 최대수요가 아니다. 세 규칙이 걸린다 ([4.2](#tech-billing-demand)) |
| **최대수요전력** | 15분 평균 전력의 최대. 순시 전력이 아니다 |
| **계약전력** | 청구서에 적힌 계약 용량. 갑Ⅰ·교육용(갑)은 이것이 기본요금 기준이다 |
| **경부하 / 중간부하 / 최대부하** | 시간대 구분. 경부하는 보통 22~08시. **요금적용전력은 경부하를 뺀다** |
| **대상월** | 요금적용전력 이월 대상. 7·8·9 · 12·1·2월. **전력량요금의 계절과 다르다** |
| **선택요금 (Ⅰ·Ⅱ·Ⅲ)** | 같은 종별 안의 요금제. 기본요금과 전력량요금 단가를 맞바꾼다 |
| **갑 / 을** | 계약전력 임계로 갈린다 (일반·산업 300 kW, 교육 1,000 kW) |
| **역률 (지상/진상)** | 유효전력 ÷ 피상전력. 지상은 유도성, 진상은 용량성 |
| **부하율** | 평균 부하 ÷ 최대 부하 |
| **기저부하** | 야간 평균 부하. 상시 가동 설비의 크기 |
| **CBL** | Customer Baseline Load. DR 정산의 기준 부하. **전력거래소가 산정한다** |
| **경제성DR** | 하루 전 자발적 입찰 수요반응. 신뢰성DR(의무 감축)은 범위 밖 |
| **kWp** | 태양광 모듈 **직류** 정격. 인버터 교류 출력과 다르다 |
| **GCR** | Ground Coverage Ratio. 모듈 면적 ÷ 부지 면적. 이격 거리의 척도 |
| **자가소비 / 잉여** | 발전량 중 그 시각 부하가 먹은 몫 / 남은 몫 |
| **첨예도 (sharpness)** | 발전 곡선의 뾰족한 정도. 감도 축이다 ([4.5](#tech-sensitivity)) |
| **요금 재계산** | 수단을 적용한 부하로 요금을 처음부터 다시 구하는 것. 절감액을 더하지 않는다 |
| **확실성 등급** | 높음 / 중간 / 중간~낮음. 산출 근거의 단단함. **어느 산출물에도 적지 않는다** (53세션) |

## 2. 시스템 구조 {#tech-architecture}

### 2.1 아키텍처 {#tech-layers}

**한 방향으로만 흐른다.** 아래 계층이 위를 부르지 않는다.

```
io ──→ quality ──→ tariff ──→ diagnose ──→ measures ──→ compare ──→ report ──→ ui
                      ↑           ↑            ↑            ↑           ↑
                    rules       pv          rules      progress     frames
```

| 패키지 | 책임 | 부르지 않는 것 |
|---|---|---|
| `io` | 파일 → `UsageData` (15분 kW·kWh·메타) | 요금·설비 |
| `quality` | 결측·정전·편중·이상치 | 요금 |
| `tariff` | 요금 계산. **순수 함수** | 설비·화면 |
| `pv` | 기상 취득·시뮬레이션·정렬·첨예도 | 요금 |
| `diagnose` | 6장 진단. **설비 정보를 받지 않는다** | 개선 수단 |
| `measures` | 7장 수단 7종 | 화면 |
| `compare` | 8장 조합 재계산 | 화면 |
| `report` | Excel·Word·차트 프레임·배치 | 화면 |
| `rules` | 기준 데이터 (전 계층이 함수로 조회) | — |
| `progress` | 진행 보고 프로토콜 | **streamlit** |
| `ui` | Streamlit 화면. **계산을 담지 않는다** | — |

**`ui` 를 뺀 어느 모듈도 `streamlit` 을 import 하지 않는다.** 시험이 이를
강제한다 (`test_progress.py`). 화면은 콜백만 넘긴다 ([4.1](#tech-flow)).

`ui` 안에서도 갈라 둔다.

| 순수 (시험이 닿는다) | Streamlit |
|---|---|
| `anchors` `text` `spec` `charts` `labels` `rules_view` `pipeline` `session` | `app` `nav` `callout` `state` `cache` `memo` `progress` `views\` |

판단이 들어가는 것(화면 순서·정렬·표기·조합 구성)은 전부 순수 쪽에 있다.

**차트는 프레임과 사양을 가른다** (15세션에 여섯을 더했다).

    report.frames    표를 만든다 — 순수. 화면과 보고서가 **같은 표**를 본다
    ui.charts        altair 사양
    report.figures   matplotlib png

각자 표를 만들면 같은 이름의 차트가 서로 다른 수를 그리게 되고, 그 어긋남은
눈으로 잡히지 않는다.

**표시 이름은 요금 계층에 있다** (`tariff.labels`). 계산 모듈이 내는 문구에도
종별 이름이 들어가는데(선택요금 전환 노트), 화면 쪽에만 두면 계산 모듈이 쓸 수
없어 `general_b/high_a/II` 가 그대로 화면에 나간다 — 15세션 통합 시험이 잡았다.

### 2.2 디렉터리와 설정 파일 {#tech-layout}

```
src/kwise/          패키지 (pip install -e .)
tools/              CLI 스크립트. 변환 로직은 src 에 두고 여기는 진입점만
tests/              pytest. 파일 하나가 계층 하나에 대응한다
data/               기준 데이터·요금표·기상 (2.3)
input/              샘플·합성 케이스 부하. 검증 재현용으로 커밋한다
docs/               요구사항서·기술서·매뉴얼
output/             산출물. casestudy_*.xlsx 만 커밋한다
cache/              중간 산출물. PROJECT_CACHE 로 옮길 수 있다
reference/          기존 pv_peak_cut 코드. **읽기 전용**
```

`pyproject.toml` 한 곳에 빌드·ruff·mypy·pytest 설정을 모았다. 설정 파일을
흩어 놓지 않는다.

### 2.3 데이터 구성 — DB 를 쓰지 않는다 {#tech-data}

**DB 를 두지 않은 이유.** 쓰기가 없다. 사용자가 올린 부하는 그 세션에서만
살고, 기준 데이터는 사람이 드물게 고치는 47여 항목이며, 기상은 읽기 전용
아카이브다. DB 를 넣으면 스키마 이관·백업·연결 관리가 생기는데 그 대가로
얻는 것이 없다. **파일이 곧 형상 관리 대상**이라는 점이 오히려 이득이다 —
`git diff` 로 요금 단가 변화를 볼 수 있다.

| 파일 | 형식 | 내용 | 갱신 |
|---|---|---|---|
| `data/tariff_kr_*.json` | JSON | 요금표 8종별 × 전압 × 선택요금 ([부록 A](#부록-a-요금-데이터-스키마)) | 엑셀 원본에서 변환 |
| `data/rules_kr.json` | JSON | **법령 유래** 27항목. 근거 조문 필수 | 화면·엑셀 |
| `data/assumptions.json` | JSON | **판단값** 25항목 | 화면·엑셀 |
| `data/defaults/*.json` | JSON | 출고값. 읽기 전용, 커밋 | 손대지 않는다 |
| `data/backup/*.json` | JSON | 편집 직전 스냅샷 최근 10개 | 자동 |
| `data/rules_history.jsonl` | JSONL | 편집 이력 한 줄씩 | 자동 |
| `data/sigungu_kr.json` | JSON | 시군구 229개 좌표 | 드물게 |
| `data/ess_cost_cases.json` | JSON | ESS 조달 사례 (회귀 원자료) | 24개월 |
| `data/ess_cost_model.json` | JSON | ESS 투자비 모델 (재적합 산출물) | 24개월 |
| `data/ess_cost_reference.json` | JSON | LCOS 참고단가 (차익거래·전망 전용) | 24개월 |
| `data/weather/*.parquet` | parquet | 기상 135격자 × 3개년, 405파일 40 MB | `fetch_weather.py` |

**기상만 parquet 인 이유.** 격자 하나·한 해가 8,760행 × 5열이다. JSON 이면
읽기가 느리고 용량이 몇 배가 된다. `int16` + 스케일 팩터로 양자화해
일사 0.1 W/m², 기온·풍속 0.01 단위로 담는다 — 계산에 충분하고 40 MB 에 들어간다.
적설은 pvlib 경로에서 쓰지 않으므로 **저장하지 않는다.**

## 3. 환경 구축과 실행 {#tech-setup}

### 3.1 설치 {#tech-install}

```
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

**가상환경은 프로젝트 안의 `.venv` 다.** 셸이 활성화하지 않은 채 실행될 수
있으므로 `.venv\Scripts\python.exe` 를 직접 부른다.

Windows 전용 사항은 `ENVIRONMENT.md` 에 있다. 요약하면 셋이다 —
파일을 열 때 `encoding=` 을 반드시 명시할 것(기본이 cp949 다), 경로는
`pathlib.Path` 만 쓸 것, Excel 저장 전 tz-aware 컬럼을 해제할 것.

### 3.2 환경변수 {#tech-env}

| 변수 | 기본값 | 뜻 |
|---|---|---|
| `PROJECT_CACHE` | `.\cache` | 기상 캐시·세션 임시 폴더 |
| `KWISE_WEATHER_DIR` | `.\data\weather` | 사전 취득분 위치. 배포 시 옮길 수 있다 |
| `KWISE_TARIFF_DIR` | `.\data` | 요금표 위치 |

### 3.3 실행 {#tech-run}

화면과 CLI 사용법은 **매뉴얼 2장**에 있다. 여기서는 진입점만 적는다.

| 진입점 | 명령 |

## 4. 핵심 로직과 계산식 {#tech-core}

**이 장이 본체다.** 결론만 적지 않고 왜 그렇게 되었는지를 남긴다.

### 4.1 처리 흐름 {#tech-flow}

```
파일 ─→ load_usage()          15분 kW·kWh·메타. 24:00 → 다음날 00:00
      ─→ check_quality()      결측·정전·편중. 보간하지 않는다
      ─→ diagnose()           부하·피크·요금 구조·계약 적정성
      ─→ load_weather()       캐시 → API → 사전 취득분 → 중단
      ─→ unit_generation_kw() 1 kWp 프로파일. **한 번만** 시뮬레이션한다
      ─→ 수단 7종             각각 요금을 다시 계산한다
      ─→ compare_combinations()  조합마다 부하를 다시 만들어 재계산
      ─→ Excel / Word
```

여덟 단계에 진행 보고가 걸린다. **계산 함수는 `progress` 를 선택 인자로 받고
`step()` 만 낸다.** 단계 경계는 부르는 쪽이 긋는다 — 한 함수가 여러 단계에
쓰일 수 있기 때문이다. 화면은 Streamlit 어댑터를, CLI 는 rich 를 붙이며
**계산 쪽은 어느 쪽인지 모른다.**

진행률 가중치는 실측값이다 ([6.4](#tech-performance)). 균등 분할하면 태양광
구간(실제 52%)에서 막대가 몇 초 멈춘 것처럼 보인다.

#### 시각 규약 — 두 가지를 구분한다 {#tech-label}

**검침 라벨은 구간 끝이다.** 하루가 `00:15` 로 시작해 `24:00` 으로 끝나 96행이
된다. 구간 시작 라벨이면 `24:00` 이 나올 수 없다.

| 쓰임 | 기준 | 이유 |
|---|---|---|
| 계절·시간대·월 **귀속** | 라벨 − 1구간 (`slot_start`) | `15:00` 슬롯은 14:45~15:00 사용량이라 중간부하다 |
| 피크 발생 **시각 보고** | 라벨 그대로 | 청구서가 그렇게 적는다 |

첫 최대부하 슬롯은 `15:15` 이다. **PV 시계열을 붙일 때 같은 규약을 써야
15분 어긋나지 않는다** — 부하 라벨 L 에 붙일 발전량은 구간 중앙 `L − Δ/2` 의
순시 출력이다. 부하는 구간 평균이고 시뮬레이션은 순시값이라, 반 칸을
빠뜨리면 7.5분, 라벨을 그대로 쓰면 15분 밀린다.

### 4.2 요금 계산 {#tech-billing}

`calculate_bill()` 이 전부다. 순수 함수이며 **기본요금과 전력량요금만**
계산한다. 기후환경요금·연료비조정액·부가가치세·전력기금은 넣지 않는다 —
모두 사용전력량에 비례하므로 **실제 절감액은 산출값보다 크다.**

#### 요금적용전력 3규칙 {#tech-billing-demand}

기본요금의 기준이 되는 kW 다. 세 조건이 겹치므로 하나라도 빠뜨리면 크게
어긋난다 (약관 제68조).

| # | 규칙 | 내용 |
|---|---|---|
| ① | **대상 시간대** | 중간·최대부하만. 경부하(22~08시)는 제외. 공휴일은 전량 경부하로 계량되므로 자동 제외 |
| ② | **대상월 한정** | max(7·8·9월, 12·1·2월, 검침 당월) — 직전 12개월 안에서. 3~6·10~11월 피크는 **이월되지 않는다** |
| ③ | **계약전력 하한** | 계약전력 × 30%. **종별로 갈리지 않는다** — 제68조 ①은 최대수요전력계 고객 전체에 걸린다. 계약전력 기준(제68조 ②) 전압에서만 적용하지 않는다 |

**①과 ②는 태양광에 반대 방향으로 작용한다.** ①은 PV 가 손댈 수 없는 야간·
공휴일 피크를 요금적용전력에서 빼 주므로 PV 에 유리하고, ②는 봄·가을 피크
저감의 가치를 없애므로 불리하다. **어느 쪽이 지배하는지는 부하 형태에 달렸다.**
케이스 스터디가 두 방향을 모두 확인했다 ([6.2](#tech-casestudy)).

`is_demand_month()` 를 `season_of()` 와 **따로 둔다.** 9월은 전력량요금상
봄·가을철이지만 대상월이고, 6·11월은 반대다. 같은 함수로 판정하면 두 규칙이
조용히 섞인다.

#### 계절·시간대·요일 {#tech-tou}

**손으로 옮겨 적지 않는다.** 값은 요금표 파일에 이미 있으므로 기준 데이터
생성 시점에 읽어 넣고, 두 벌이 어긋나지 않는지 시험이 지킨다.

> 옮겨 적기를 실제로 틀렸다. 여름 중간부하를 `[[8,11],[12,13],[18,22]]` 로
> 적었는데 실제는 `[[8,15],[21,22]]` 였다. 그 자리에서 규칙이 생겼다.

| 요일 | 계량 |
|---|---|
| 평일 | 그대로 |
| 토요일 | 최대부하 → **중간부하**. 경부하가 되는 것이 아니다 |
| 일요일·공휴일 | 전량 **경부하** |

**일요일도 공휴일로 계량한다.** `holidays` 라이브러리가 일요일을 담지 않는데
관공서 공휴일 규정에는 포함된다. 빠뜨리면 연 52일이 최대부하로 잘못 계량된다.

#### 기본요금 기준 — 갈림길은 갑/을이 아니라 전압이다 {#tech-base-fee}

제68조 제1항·제2항이 **최대수요전력계 설치 여부**로 가르고, 제38조 제2항이
그 설치를 **공급전압**으로 정한다 — 「고압 이상의 전압으로 전기를 공급받는
고객에게는 최대수요전력과 무효전력을 계량할 수 있는 전력량계를 설치합니다」.

**89세션에 전압별로 갈랐다.** 기준은 종별 속성이 기본값이고 전압이 그것을
덮는다 — 요금 데이터의 `voltages\<전압>\base_fee_basis` 다.

| 종별·전압 | 갖는 전압 | 기준 | 근거 |
|---|---|---|---|
| 을 (일반·산업·교육) | 고압만 | **요금적용전력** | 제38조 ② → 제68조 ① |
| **갑Ⅱ** (일반·산업) | 고압만 | **요금적용전력** | 제38조 ② → 제68조 ① |
| **교육용(갑) 고압A·B** | 저압 + 고압 | **요금적용전력** | 제38조 ② → 제68조 ①. 교육용에는 갑Ⅱ 가 없어 아래 단서가 서지 않는다 |
| 교육용(갑) **저압** | 저압 + 고압 | **계약전력**. 모르면 멈춘다 | 제38조 ③은 「설치할 수 있다」(재량) → 제68조 ② |
| 갑Ⅰ (일반·산업) **전 전압** | 저압 + 고압 | **계약전력**. 모르면 멈춘다 | 제57조 ④·제59조 ⑤가 갑 고압을 갑Ⅱ 로 보낸다 — 갑Ⅰ 고압 행은 저압계량 예외 경로 |

섞으면 기본요금이 통째로 틀린다. **읽을 때 전압을 빼지 않는다** —
`ContractType.base_fee_on_contract_at(voltage)` 하나로만 읽는다. 89세션 전에는
전압 없는 프로퍼티였고, 그래서 교육용(갑) 고압이 **14.5배**로 나왔다.

> **갑Ⅱ 는 61세션에 요금적용전력으로 옮겼다.** 60세션까지는 갑 전체를
> 계약전력 기준으로 두었고, 용인 소규모 건물(갑Ⅱ 고압A, 계약전력 290 kW)
> 실측에서 기본요금이 **연 2,864만원**으로 나왔다 — 청구서는 요금적용전력
> 118 kW 기준이었다.
>
> **계약전력으로 매긴 자리에는 경고가 남는다.** 전압은 이제 알지만
> **최대수요전력계가 실제로 섰는지**는 청구서를 봐야 안다 — 갑Ⅰ 고압 행은
> 저압계량을 전제하고, 저압은 설치가 재량이다.
>
> **교육용(갑) 고압의 하한은 30% 다** (90세션에 세칙 원문을 읽고 닫았다).
> 제68조 ①의 30% 는 최대수요전력계 고객 전체에 걸리고 종별로 갈리지 않는다 —
> 고압에서 그 항을 타는 이상 하한도 함께 온다. **교육용(을)의 15% 는 종별
> 특례가 아니었다** — 시행세칙 별표4 8.「초·중·고교 및 유치원 전기요금 적용」
> 은 약관 제58조 적용대상 **중** 초·중등교육법 제2조와 유아교육법 제2조 제2호
> 시설에만 붙고 「고객의 신청일이 속하는 월분부터」 적용한다. 그래서 **교육용
> 둘 다 30%** 로 옮겼다.

#### 역률요금 {#tech-power-factor}

기본요금에 대한 **추가·감액**이다. 경고로 둘 수 없다 — 기본요금의 −1.0% ~
+6.4% 이고 샘플에서 1%가 453만원이다.

```
주간 08~22시  지상 기준 92%. 미달 시 1%p당 +0.2% (60%까지)
                            초과 시 1%p당 −0.2% (97%까지)
야간 22~08시  진상 기준 95%. 미달 시 1%p당 +0.2%
              단, 지상이면 100%로 간주 → 추가 0
```

**야간 진상 페널티는 '역률 개선 설비 과투자의 결과'다.** 제43조 ② 2호 나목이 지상이면
100%로 간주하므로, 대부분의 건물은 야간 경부하에서 지상이라 추가가 0 이다.
진상은 고정형 역률 개선 설비가 부하 대비 과다할 때만 생긴다. 그래서 이 조항은 "야간에도
역률을 관리하라"가 아니라 **"주간 역률을 맞추려 역률 개선 설비를 키우면 야간에 되돌려
받는다"**로 읽어야 한다.

**92% 가 두 조문에서 온다. 항목을 갈라 두었다.**

| 항목 | 조문 | 뜻 |
|---|---|---|
| `power_factor.lagging_standard_pct` | 제41조·제43조 ② | 역률요금의 **기준** |
| `power_factor.deemed_lagging_pct` | **제42조** | 무효전력계 미설치 시 **간주값** |

오늘은 둘 다 92% 라 묶고 싶어진다. 묶으면 **기준만 90 으로 개정됐을 때
역률을 모르는 고객의 값까지 따라 내려가** 조정액이 0 이 아니게 된다 —
실측하지 않은 값으로 금액이 생기는 것이다.

우리 데이터는 15분 유효전력뿐이라 제42조의 30분 누적 계량을 재현할 수 없다.
기본값 92%는 지어낸 값이 아니라 **그 조항이 무효전력계 미설치 고객에게
적용하는 간주값**이고, 그 값에서 조정액이 정확히 0 이다.

제43조 ③(첫 달 예고)은 **계산에 넣지 않는다.** 첫 달을 빼면 기간에 따라
금액이 달라져 도입 전후 비교(Δ)가 흔들린다.

#### 결측 월과 부분 월 {#tech-partial}

**결측을 보간하지 않는다.** 결측률이 문턱(5%)을 넘는 달은 관측 기준과 결측
보정 기준을 **함께** 낸다. 어느 쪽도 정답이라고 말하지 않는다.

부분 월은 기본요금을 **13개월분 부과하지 않기 위해** 계수를 곱한다. 기본
정책은 `merge` — 앞뒤 두 부분 월을 합쳐 한 달로 본다. 샘플에서 정확히
12.00개월분이 된다. 짝이 없으면 일수 비례로 물러서고 그 사실을 `notes` 에 적는다.

기간이 12개월 미만이면 **'연간'이라 부르지 않는다.** 실제 기간이나 12개월
환산으로 표기하고 환산 시 경고를 붙인다.

### 4.3 개선 수단별 산식 {#tech-measures}

**절감액은 언제나 재계산이다.** 수단을 적용한 15분 부하를 만들어
`calculate_bill()` 을 다시 부른다. 비율로 어림하지 않는다.

| # | 수단 | 산식 요지 | 확실성 |
|---|---|---|---|
| 7.1 | 선택요금 전환 | 같은 종별·전압의 모든 선택요금으로 요금을 다시 계산해 최소를 고른다 | 높음 |
| 7.2 | 계약전력 조정 | **하한이 최대수요를 넘을 때만** 목표(최대수요 ÷ 하한비율)와 금액이 난다 | 높음 |
| 7.3 | 경제성DR | 거래 가능일 × 등록 용량 × 입찰 시간 = 감축 가능량(kWh) | 중간 |
| 7.4 | 역률 개선 | 두 역률에서 각각 요금을 계산해 차를 낸다 | 높음 |
| 7.5 | 태양광 | 용량 곡선 20단계. 각 점에서 순부하를 만들어 재계산 | 중간 |
| 7.6 | ESS | 목표 요금적용전력에서 출력·용량을 역산하고 디스패치 후 재계산 | 중간~낮음 |

**7.7 잉여 활용은 41세션에 빠졌다.** 잉여는 태양광을 얼마나 크게 지을지에 따라
나오는 **결과**이지 따로 고르는 수단이 아니다 — 처리 선택(상계·외부 판매·출력제어)을
7.5 안으로 옮기고 개선안을 여섯으로 줄였다. 계산 모듈
(`kwise.measures.surplus`)은 그대로 남는다.

**순서는 투자비 순으로 확정했고 바꾸지 않는다. 번호도 밀지 않는다.** 수단을 더하거나
뺄 때마다 번호가 밀리면 코드 docstring 과 문서 참조가 계속 어긋난다. 목록은
`kwise.measures.MEASURE_CATALOG` 한 곳에 있고 화면과 보고서가 함께 읽는다.

#### 7.1 선택요금 전환 {#tech-tariff-switch}

**같은 계약종별 안에서만 비교한다.** 종별은 용도로 정해지는 계약이지 고를 수
있는 요금제가 아니다. **전압구분도 현행에 가둔다** — 고압A(3.3~66 kV)와
고압B(154 kV)는 수전설비가 물리적으로 다르다. 단가만 보면 그럴듯한 권고가
나와서 더 위험하다.

드롭다운 생성(`list_selections`)은 가두지 않고 **전환 비교**(`switchable_selections`)만
가둔다. 둘은 쓰임이 다르다.

#### 7.2 계약전력 조정 {#tech-contract}

**하한 규정을 모르면 금액을 산출하지 않는다.** 일반용(을) 기본요금은
요금적용전력 기반이므로, 계약전력을 낮춰도 요금적용전력이 그대로면 요금이
그대로다. 줄어드는 경우는 하한(계약전력의 30%)에 걸려 있을 때뿐이다.
모르는 채로 금액을 내면 **없는 절감을 만들어내는 것**이 된다.

**목표 계약전력은 최대수요 ÷ 하한비율이다** (83세션). 약관에서 바로 나오는
수이고, 그 아래로 내려도 더 얻을 것이 없는 상한이다. 「요금적용전력 ×
(1 + 여유율)」 이라는 권장값과 판단값 `contract.margin_ratio`·`contract.margin_range`
는 **걷어냈다** — 전자는 기본요금이 **계약전력**에 붙는 종별(갑Ⅰ·교육용(갑))의
산식이라 을·갑Ⅱ 에서는 전제가 서지 않았고, 여유율 폭에는 근거가 없었다.
61세션이 갑Ⅰ/갑Ⅱ 를 가르며 기본요금 기준을 바로잡았을 때 따라왔어야 할
변경이다 — **전제가 사라진 결정**이 두 세션을 넘어 남아 있었다.

하한이 지는 갈래에서는 **하향 경고(`contract.margin`·`contract.penalty`)를 내지
않는다.** 낮출 자리가 없는데 「되돌리기 어렵다」 를 읽히면 하지도 못할 일을
조심하라는 말이 된다. 요구사항서 9.4 의 필수 경고는 Excel 요약과 Word 가 언제나
싣는다.

#### 7.3 경제성DR {#tech-dr}

근거는 전력시장운영규칙 제12장이다. **신뢰성DR 은 범위 밖이다.**

**거래일 제약이 이 절의 핵심이다** (제12.4.2.1조 1항 1호) — 공휴일과 **토요일**을
제외한 평일만 입찰할 수 있다. 빼면 감축 가능량이 30% 이상 과대평가된다
(샘플 359일 중 245일).

> **요금 계량의 '평일'과 다르다.** 요금 엔진은 토요일을 최대부하 → 중간부하로
> 낮출 뿐 공휴일로 보지 않는다. DR 은 토·일·공휴일이 모두 제외다. 그래서
> `dr_day_mask()` 를 따로 둔다. 같은 함수로 판정하면 두 규칙이 조용히 섞인다.

**연간 참여 일수 제한은 없다** (14세션에 바로잡았다). 13세션에 넣었던 「연 60시간
한도」는 전력거래소 확인 결과 경제성DR 의 제약이 아니었다. 남는 제약은 셋이다.

| 제약 | 값 |
|---|---|
| 하루 한도 | 최대 2회 × 1회 1~4시간 = **하루 8시간**. **판단값이다** — 아래를 본다 |
| 참여 요일·시간 | 평일만 (토·일·공휴일 제외), 09:00~12:00 · 13:00~20:00 |
| 미이행 제재 | **6개월 입찰 제한** |

**하루 한도 둘은 조문이 정한 수가 아니다** (87·88세션에 규칙을 뒤졌고 89세션에
옮겼다). 「1회 1~4시간」 이 나오는 곳은 제12.3.2.1조 언저리의 **감축시험**
규정이고, 「하루 최대 2회」 의 상한 조문은 아예 없다(별표28 3.2.5 는 2회 이상
발령됐을 때의 고객기준부하 산정 규정이다). 그래서 둘 다 `assumptions.json` 에
있고 화면에 **[판단]** 으로 보인다. 나머지 DR 값은 `rules_kr.json` 그대로다.

**따라서 실질 제약은 「감축할 여력이 있는 날이 며칠이냐」 하나다.** 데이터에서
찾는다.

    ① 기준선     주말·공휴일의 판정 시간대 평균 부하 (시장 시간대 ∩ 건물 운영 시간대)
    ② 저부하 평일 대상일 중 그 시간대 평균이 기준선 × 1.2 이하인 날 (배수는
                 assumptions.json 의 `dr.low_load_multiple`)
    ③ 감축 여력   평일 정상 평균 − 그날 실제 부하
    ④ 참여 시간   하루 8시간 상한, 저부하가 실제로 지속되는 시간까지
    ⑤ 감축 가능량 Σ(저부하일별 감축 여력 × 그날 참여 가능 시간)

샘플에서 저부하 평일은 **이틀**(2023-05-01·2023-10-02)이고 감축 가능량은
31,133 kWh/년이다. 걸린 두 날 모두 사무실을 비운 날이라, 하위 분위수 방식이
「항상 그만큼」 을 뽑던 것과 달리 **없으면 없다고 낸다.**

**보수적으로 산정한다.** 미이행이 6개월 입찰 제한이라 과대 산정의 대가가 크다.
등록 권장값은 **저부하일 감축 여력 분포의 하위값**이다 — 평균으로 등록하면
절반의 날에 미달하고 미달은 제재다 (별표26).

**저부하 평일 목록을 화면에 낸다.** 창립기념일·워크숍처럼 사무실을 비우는 날일
가능성이 높아, 그 날이 맞는지는 사용자가 판정한다.

**정산 단가에 기본값을 두지 않는다.** 전력거래소 월별 순편익가격 + 사업자
수수료라 우리가 만들 수 없다. 없으면 감축량(kWh)만 낸다.

**기본요금 절감을 계산하지 않는다.** SMP 기준 산발 입찰이라 참여일이 연중
최대수요일과 겹칠 확률이 낮다. 편익은 정산금 하나다.

0.1 MW-h 문턱(제12.4.2.1조 1항 2호)은 **수요관리사업자가 묶은 자원 단위**
기준이라 개별 고객 판정이 아니다. 참고 표시만 한다.

#### 7.5 태양광 {#tech-solar}

**기본 입력은 넷이다** — 설치 가능 면적·설치 밀도·지역·방위 (15세션에 방위를
더했다).

발전량 예측 R² 가 0.8 이라 **입력 정밀도가 기상 오차를 이길 수 없다.** 게다가
용량 곡선이 20단계를 훑으므로 면적 환산이 ±20% 틀려도 곡선 위 다른 점을 볼
뿐이다. 상세 입력은 확장 패널로 접는다. **모드를 나누지 않는다** — 상세 설계
모드를 만들면 pvsim 과 경계가 흐려진다.

```
설치 용량(kWp) ≈ 설치 가능 면적 × GCR ÷ 5
```

모듈 효율 20% 기준 1 kWp 당 약 5 m² 다. **밀도 하나가 GCR 과 경사각을 함께**
정한다 — 고밀도 배치는 이격을 좁히는 대신 경사를 낮춰 음영을 줄이는 실무
관행이다.

| 밀도 | GCR | 경사 | 1,000 m² | 상충 |
|---|---|---|---|---|
| 높음 | 0.55 | 15° | 110 kWp | 면적당 용량 최대, kWp당 발전량 최소 |
| 보통 | 0.40 | 25° | 80 kWp | 균형점 (기본값) |
| 낮음 | 0.30 | 30° | 60 kWp | kWp당 발전량 최대, 용량 최소 |

**용량 곡선은 시뮬레이션 1회 + 곱셈이다.** pvwatts 직류와 인버터 모델이 정격에
선형이다(정격과 인버터 용량이 함께 커진다). 20단계라도 태양 위치 계산은 한 번이며
선형성을 시험이 고정한다. 되풀이한다면 20단계 × 감도 3 = 60회가 되어 그것이
최대 병목이 된다 — 실측으로 확인했다 ([6.4](#tech-performance)).

**일몰 후 발전량을 태양 고도로 잘라낸다.** 시간별 → 15분 선형 보간이 일몰을
가로질러 값을 흘리기 때문이다.

**방위는 8방위로 받는다** (15세션). 45도 간격이면 최대 오차 22.5도이고 발전량
차이가 1–2% 라 예측 오차 안에 묻힌다. 선택지 라벨에 상대 발전량을 병기하는데
**하드코딩하지 않는다** — 고른 지역·경사각으로 여덟 방위를 각각 돌려 남향 대비
비율을 낸다. 경사가 낮으면 방위 영향이 줄기 때문이다.

| 경사 | 남 | 남동 | 남서 | 동 | 서 | 북 |
|---|---|---|---|---|---|---|
| 25° (밀도 보통) | 기준 | −8% | −1% | −20% | −10% | −31% |
| 15° (밀도 높음) | 기준 | −5% | −1% | −13% | −7% | −19% |
| 90° (벽면) | 기준 | −18% | −1% | −40% | −21% | −64% |

시뮬레이션 여덟 번이라 0.85초다. 용량을 1 kWp 로 고정하므로 **면적·밀도를 바꿔도
비율이 같고**, 캐시가 지역·경사·손실로 걸린다.

**벽면 어레이를 함께 올릴 수 있다.** 지붕과 방위를 따로 고르고 경사 90°·GCR 1.0
으로 계산한다. 단위 프로파일은 두 어레이를 합쳐 총용량으로 나눈 값이라 섞인 방위가
그대로 반영된다 (`PvSystemConfig.scaled()` 이 비율을 유지한다).

**용량은 한 줄로 판정한다** (15세션 1-3). 20단계를 훑는 것은 그대로지만 표를
화면에 나열하지 않는다.

    회수기간이 있으면  그 최소점
    없으면(단가 미입력) 절감액(역률 악화분을 뺀 값) 최대점

**새 산식을 만들지 않는다** — 이미 훑은 점에서 고르기만 한다
(`SolarCurve.verdict()`). 무엇이 그 용량에서 멈춰 세웠는지(면적 상한 / 잉여 발생 /
기본요금 절감 포화)를 판별해 화면에 한 줄 적는다. 화면에는 대표 다섯 지점을
표로 내고 곡선은 접어 둔다. 20단계 상세는 Excel 「태양광 용량 곡선」 시트로 간다.

**회수기간이 평평하면 최소점을 그냥 고르지 않는다** (16세션 0-4). kWp당 단가면
투자비도 절감액도 용량에 비례해 회수기간이 용량과 거의 무관해진다 — 실측에서
8 kWp 가 8.060년, 상한 160 kWp 가 8.114년이었다. 최소점을 그대로 고르면 상한의
1/20 이 답이 된다. 0.7% 차이는 발전량 예측 오차(R² 0.8) 안이므로, 최소
회수기간의 `pv.payback_tie_ratio` 안에 드는 점 가운데 절감액이 큰 것을 고른다.
잉여로 회수기간이 실제로 꺾이면 꺾인 뒤 점들이 이 폭을 벗어나 최소점이 남는다.

**참고단가를 제공하지 않는다.** ESS 는 에너지경제연구원 LCOS 연구를 인용할 수
있지만 태양광은 확보하지 못했다. 단가를 넣지 않으면 투자비는 **0원이 아니라
미산출**이고 사유가 붙는다. 0원으로 두면 회수기간이 0년으로 나와 "즉시 회수"로
읽힌다. 용량 곡선의 모든 점에 같은 kWp당 단가를 적용하므로 **규모의 경제가
반영되지 않는다** — 소규모 구간의 회수기간이 낙관적으로 나온다.

#### 7.6 ESS {#tech-ess}

목표 요금적용전력에서 출력·용량·방전시간을 역산한다.

**목표를 사용자가 찍게 두지 않는다** (14세션에 바꿨다). 피크의 90%에서는 용량이
4,094 kWh 로 사례 범위를 훌쩍 넘고, 조금만 올리면 방전시간이 0.44시간까지 줄어
고출력 셀이 된다. 그 사이 어딘가에 회수기간 최소점이 있으므로 **훑어서 찾는다.**

    필요 출력 = 초과분 최대값 (kW)
    필요 용량 = 하루치 초과 에너지 합의 연중 최대값 (kWh)
    과금 용량 = max(정격 용량, 시장 최소 100 kWh)
    규격 사양 = 정격을 살 수 있는 규격으로 올림          ← **화면에 내는 사양**
    투자비   = 고정비 + 용량단가 × 규격 용량 + 전기공사
    절감액   = 저감량(kW) × 기본요금단가 × 12       ← **현행 요금제** 기준
    회수기간 = 투자비 ÷ 절감액

**기본요금단가는 현행 요금제 기준이다.** 최적 요금제로 바꾼 뒤의 단가를 쓰면 ESS
절감액이 선택요금 전환에 딸려 움직여 2단계 독립 평가가 깨진다.

**격자를 10 kW 이하로 둔다.** 곡선이 격자에 민감하다 — 50 kW 간격이면 5,200 kW
27.2년에서 멈추고, 10 kW 간격이라야 5,180 kW 26.6년을 찾는다.

**개략 회수기간 곡선은 U자다.** 왼쪽은 **고정비가 지배해** 용량을 줄여도 투자비가
그만큼 줄지 않는 구간이고, 오른쪽은 용량이 급증해 투자비가 늘어나는 구간이다.
**물리적 최소가 아니라 조달 구조의 산물이다.** 아래 검산값이 그 곡선의 값이다.
**목표 슬라이더는 없다.**

> 49세션까지는 왼쪽 팔의 이유를 「시장 최소 규모 100 kWh」 로 적었다. 50세션에
> 그 하한을 **규격 격자**로 바꾸면서 살 수 있는 최소 배터리가 50 kWh 로
> 내려갔는데 **U자는 그대로다** — 1억을 넘는 고정비와 전기공사비가 왼쪽 팔을
> 만든다. 하한이 원인이라 적어 두었던 것은 **하한이 눈에 띄었기 때문**이지
> 그것이 유일한 원인이어서가 아니었다.

**U자라는 설명은 개략 곡선에만 해당한다** (40세션). 요금을 다시 계산한 곡선은
골짜기가 여럿이다 — 39세션 조사에서 국소 최소가 샘플 2개·C2 7개·C3 5개·C5 5개였고,
C5 는 회수기간 차가 0.76년인데 용량이 3배인 골짜기가 둘이었다. **그래서 삼분
탐색·성긴 격자를 쓰지 않는다** — 둘 다 C5 에서 엉뚱한 골짜기로 빨려 들어갔다.

**개략 곡선은 화면·산출물에 없다** (46세션). 목표를 고르는 데만 쓰고, 사람이
보는 것은 정밀화 21점에서 뽑은 **목표별 사양 표**다 — `frames.ess_spec_frame`.
곡선을 내보내던 `ess_target_chart`·`ess_payback_png`·`ESS_PAYBACK_AXIS` 는 지웠다.

**왜 곡선을 비율로 올리지 않았나.** 곡선 값과 카드 값의 비를 자료 일곱 121점에서
재 봤더니 **1.101~3.179** 로 갈렸다 (샘플 1.19~1.32 · C3 1.10~2.58 · C5 3.08~3.18).
투자비배는 어디서나 1.00 인데 절감액배가 0.32~1.04 로 갈리기 때문이다 — 곡선은
저감량 × 기본요금단가 × 12 로 어림하고 실제는 요금적용전력(롤링 최대)이 정한다.
**한 곱수로는 못 옮긴다.**

    | 갈래 | 표에 세우는 줄 |
    |---|---|
    | 목표별 사양 표 | 창의 양 끝 · 최단 회수기간 · 가장 넓은 틈부터 반씩 — 다섯 줄 |

**목표는 개략 곡선이 아니라 정밀화가 정한다** (`refine_ess_target`).
개략 최소 ±2%(`ess.refine_window_ratio`)를 곡선과 **같은 격자**로 훑되, 각 점을
`evaluate_ess` 와 같은 산식으로 잰다 — 디스패치를 돌려 요금을 다시 계산하고
투자비를 정격 용량으로 매긴다. 샘플은 21점에 약 8초다.

**격자를 곡선과 같게 두는 이유가 셋이다.** ① 표식이 곡선 위에 찍혀야 한다
② 목표는 계약·설정에 적는 값이라 눈금에 맞아야 한다 ③ 1 kW 격자는 201점 84초다
(샘플에서 5,175 kW·30.35년을 더 찾지만 곡선 전체를 1 kW 로 다시 그려야 한다).

**격자와 창은 요금적용전력의 비율이다** (`ess.target_step_ratio` 0.2% ·
`ess.refine_window_ratio` 2%). 48세션에 절대 kW 에서 바꿨다 — 10 kW 는 5,293 kW
짜리 건물에서 0.19% 지만 265 kW 짜리에서는 3.8% 라 곡선이 8점밖에 안 나왔고,
±100 kW 창이 그 곡선 전체(폭 79 kW)를 덮어 **가장자리 검사가 구조적으로 못
떴다.** 비율을 씌운 뒤 **1·2·5 눈금**에 맞추므로(`snap_step_kw`) 목표는 여전히
읽히는 값이고, 샘플은 10 kW·±105.9 kW 로 옛 값과 같은 21점을 훑는다.

**창을 검증한다.** ±2% 는 자료 일곱에서 나온 값이라 벗어나는 자료가 있을 수
있다. 최소가 창 가장자리에서 잡히면 두 배로 넓혀 다시 훑고
(`ess.refine_max_widen` 회까지), 그래도 가장자리면 **경고를 남긴다**
(`ess.refine_at_edge`) — 조용히 자르면 「그 자리가 최소」 로 읽힌다.

**「최적」 이라 부르지 않는다** (49세션). ESS 가 고른 자리의 이름은
**「최단 회수기간」** 이다 (`kwise.measures.base.SHORTEST_PAYBACK`).

**태양광은 「권장」 이다** (50세션 — `RECOMMENDED`). 이름을 셋으로 가른 것은
**규칙이 셋이기 때문이다.**

    | 자리 | 고르는 규칙 | 표식 |
    |---|---|---|
    | ESS 목표 | 후보 가운데 회수기간 최소 | 최단 회수기간 |
    | 태양광 (단가 있음) | 최소의 `pv.payback_tie_ratio` 안에서 절감액 최대 | 권장 |
    | 태양광 (단가 없음) | 절감액 최대 | 최대 절감액 |

49세션이 태양광에도 「최단 회수기간」 을 붙이면서 **16세션의 동률 처리와
어긋났다.** 소형 사무빌딩에서 40 kWp 11.0년 위에 48 kWp 11.1년이 서고 표식은
뒤쪽에 붙는다 — 계산은 옳고 이름이 틀렸다. 「권장」 은 규칙을 드러내지 않으면서
사실과도 어긋나지 않는다. **판정 근거는 화면 표 아래 한 줄이 적는다**
(`payback_tie_note` — 비율을 기준 데이터에서 읽는다). 출처 표기는 매뉴얼로
보내지만 판정 근거는 결과를 읽는 데 드는 설명이라 화면에 남는다 (50세션).

### 표식 어휘를 한 곳에 뒀다 (51세션 1절)

50세션이 이름 **셋**을 `measures.base` 에 뒀는데 **나머지 표식은 문자열로
흩어져** 있었다 — `report.frames` 에 「선정 용량」·「면적 초과」, `ui.pipeline` 에
「잉여 시작」·「잉여 다량」. 그래서 두 가지를 아무도 못 잡았다.

    권장 == 면적 상한   「선정 용량」 에 먹혀 「권장」 이 표에서 사라졌다
    단가 없음          표식은 「최대 절감액」 인데 각주만 「권장」 을 말했다

**둘 다 각주와 표가 다른 출처를 읽어서 생긴 일이다.** 이름을 전부
`measures.base` 로 옮기고, 표를 만드는 자리에 날문자열이 남지 않는 것을 시험이
지킨다 (`test_표식_이름이_한_곳에서_온다`).

**「선정 용량」 과 「권장」 은 다른 사실이다.** 앞은 설치 가능 면적이 허용하는
상한이고 뒤는 동률 처리를 거쳐 고른 자리다. 50세션은 둘이 다를 때만 뒤를 찍었는데,
**같을 때도 둘 다 적는다** — 「지을 수 있는 가장 큰 것이 곧 권하는 것」 도 사실이다.

**각주는 규칙이 실제로 쓰일 때만 붙는다** (`CapacityVerdict.tie_note`).

### 판정 문구를 둘로 갈랐다 (52세션 1절)

51세션까지 화면은 「**용량 판정** — …」 한 줄과 근거 한 줄을 늘 냈다.
**두 자료에서 다 어긋났다.**

    대형   「설치 가능 면적 전체(160 kWp)를 쓰는 것이 회수기간 기준 가장
          유리합니다」 — 회수기간은 56 kWp 가 짧다. **거짓이다**
    소형   「권장 용량은 48 kWp 입니다」 — 카드는 160 kWp 로 계산하는데
          참고값이 계산에 쓰인 값처럼 읽힌다

**하는 일이 다른 두 문장을 한 문장에 욱여넣은 것이 원인이다.**

    ① headline(area_m2)          무엇을 계산했나 — 선정 용량과 그 값이 나온 까닭
    ② reference_note(free_kwp)   참고 — 선정 용량과 다를 때만

①은 판정이 아니라 **사실**이다. 카드가 쓰는 값은 언제나 「선정 용량」 이고
(`curve.points[-1]`), 면적이 입력이므로 「면적을 다 쓴 N kWp 로 계산했습니다」 가
그 사실을 그대로 적는다. ②는 권장·잉여 한계가 선정 용량과 **다를 때만** 나온다.

`basis_sentence` 와 「그 용량에서 멈춘 것은 **○○** 입니다」 배지는 지웠다 —
①이 그 말을 이미 하고, 배지가 문장 중간에 박혀 읽기 어려웠다.

**표식 넷의 뜻을 코드에 뒀다** (`base.CAPACITY_MARKS`). 51세션이 이름을 모았지만
**뜻은 도크스트링에만** 있어, 문구를 쓰는 자리에서 읽을 수 없었다.

| 표식 | 뜻 |
|---|---|
| 선정 용량 | 입력(면적)에서 나온 값. 카드가 이 값으로 계산한다 |
| 권장 | 동률 폭 안에서 절감액이 가장 큰 줄. 판정 규칙의 결과다 |
| 잉여 시작 | 여기부터 잉여가 난다 |
| 잉여 다량 | 잉여가 많이 난다 |

**「권장」 을 「잉여 없는 최대」 로 바꾸지 않는다 — 다른 사실이다.** 대형의 잉여
없는 최대는 2,038 kWp 인데 「권장」 은 160 kWp 에 붙는다. ②의 잉여 한계는
`surplus_free_capacity_kwp` 에서 읽는다 — 51세션까지는 「권장 48 kWp, **그
이상은** 잉여가 발생」 이라 적었는데 잉여는 **40 kWp 부터** 난다.

**48 과 40 이 다른 까닭.** 곡선은 면적 상한을 20단계로 자르므로 2,000 m² 면
눈금이 8 kWp 다 — 잉여 한계 40.24 kWp 는 그 눈금에 없다. 권장은 눈금 위의 한
점이고 잉여 한계는 닫힌 식의 정확값이다. **표의 「잉여 시작」 줄만 곡선 밖에서
따로 만든다** (`surplus_capacity_points`).

**자가소비율은 내림으로 자른다** (`_self_consumption`). 눈금 한 칸 위에서 잉여가
33.7 kWh(발전량의 0.06%)뿐이라 반올림하면 100.0% 로 찍혔는데, 그 줄 아래에
「잉여 시작」 이 붙어 **표가 스스로 어긋나 보였다.** 「100.0% ⟺ 잉여 0」 이
표 안에서 맞아야 한다.

### 회수기간이 평평한 표를 어떻게 읽히게 하나 (51세션 2절)

kWp당 단가면 투자비와 절감액이 함께 용량에 비례해 **회수기간이 용량과 거의
무관해진다** (16세션 0-4). 대형 샘플에서 56·104·160 kWp 가 6.2·6.3·6.3년이다.
표가 그대로 보이면 **「어느 것을 골라도 같다」 로 읽히는데** 절감액은
1,078만 → 1,996만 → 3,065만원/년으로 **세 배 차이 난다.**

    ① 절감 열 둘을 하나로 합쳤다   줄을 가르는 것은 합계다
    ② 동률 폭 안의 줄에 「동률」    각주와 이어져 「그중 절감액이 큰 쪽」 이 읽힌다

**동률 폭은 곡선의 최소에서 잰다** — `capacity_verdict` 와 똑같은 식이라야 한다.
고른 자리에서 재면 밴드가 한 번 더 넓어져, **규칙이 동률로 보지 않은 줄에**
「동률」 이 붙는다 (소형에서 56 kWp 가 그랬다).

### 줄 고르기 — 표식이 붙은 줄은 버리지 않는다 (51세션 4절)

50세션까지는 지점을 오름차순으로 늘어놓고 앞에서 `CAPACITY_ROWS` 개만 잘랐다.
권장이 면적 상한과 다르면 지점이 여섯이 되는데 **가장 큰 것 — 곧 「선정 용량」 —
이 버려졌다.** 카드가 낸 용량이 비교 표에 없는 것이라 매뉴얼과도 어긋났다.

버릴 것은 **표식 없는 줄**뿐이고, 그중에서도 **옆 줄과 가장 가까운 것**부터
버린다 (`_capacity_rows`) — 곡선 모양을 가장 적게 해친다. 표식이 `CAPACITY_ROWS`
를 넘으면 자르지 않는다: **표식이 곧 그 줄을 세운 이유다.**

「최적」 은 판단이 들어간 말이라 **「그것을 하라」 로 읽힌다.** 소형 사무빌딩에서
회수기간 578년짜리가 「최적 목표」 로 나왔는데, 성립 조건을 늘려 지우는 것은
답이 아니었다 — 규모 조건까지 걸면 대형 샘플의 5,170 kW 도 탈락한다. **이름이
틀린 것이다.** 「최단 회수기간」 은 사실만 말하므로 578년이어도 거짓이 아니고,
수명을 넘는다는 판단은 `ess.payback_over_warranty` 경고가 따로 한다.

**선택요금 전환의 「최적 요금제」 는 그대로 둔다** — 회수기간이 아니라 금액이
가장 적은 요금제이고, 투자가 없어 「최적」 이 사실과 어긋나지 않는다. ESS
디스패치 한계를 적는 「최적 운전」(MILP 최적제어)도 다른 뜻이라 그대로다.

**코드 식별자는 바꾸지 않았다** — `EssOptimum`·`refine_ess_target`·
`CapacityVerdict.best` 는 그대로이고, 각 도크스트링에 화면 이름을 적어 두었다.

**후보에서 빼는 것이 둘이다** (48세션).

    목표 미달   디스패치가 목표를 못 지킨 점 (`DispatchResult.target_met`).
                「목표 210 kW」 이라 적고 실제 요금적용전력이 264 kW 면 그 목표의
                ESS 가 아니다. 표에는 남기되 「목표 미달 (실제 264 kW)」 표식을 단다
    마진 미달   kW당 배터리비(`용량단가 × 방전시간`)가 10년 기본요금 절감액
                (`기본요금단가 × 12 × 10`)을 넘는 점. 규모를 어떻게 잡아도
                회수되지 않는다 (`viable_discharge_hours` — 샘플에서 1.031시간)

**둘은 한 뿌리다.** 방전시간이 경부하 충전 창보다 길어지면 배터리를 하룻밤에
되채우지 못해 목표를 놓치고, 같은 방전시간이 kW당 배터리비도 밀어 올린다.
마진 조건이 훨씬 빡빡하므로 실무에서는 그쪽이 먼저 걸린다.

**성립하는 점이 하나도 없으면 목표를 제시하지 않는다.** 창을 훑는 대신 곡선
전체에 벌려 잡은 다섯 점만 재고 결론을 낸다 (`NOT_VIABLE_CONCLUSION`) —
「어떤 목표에서도 kW당 배터리비가 10년 기본요금 절감액을 넘습니다.」 사양 표는
참고로 남는다. C6 야간 피크형이 이 자리다.

| 목표 | 저감 | 필요 용량 | 정격 용량 | 규격 사양 | 투자비 | 회수기간 |
|---|---|---|---|---|---|---|
| 5,200 kW | 93 kW | 35 kWh | 41 kWh | 100 kW / 50 kWh | 2.20억 | 27.2년 |
| **5,180 kW** | **113 kW** | **72 kWh** | **85 kWh** | **150 kW / 100 kWh** | **2.62억** | **26.6년** |
| 5,170 kW | 123 kW | 101 kWh | 120 kWh | 150 kW / 150 kWh | 3.04억 | 28.4년 |
| 5,150 kW | 143 kW | 183 kWh | 216 kWh | 150 kW / 250 kWh | 4.05억 | 32.6년 |
| 5,100 kW | 193 kW | 432 kWh | 512 kWh | 200 kW / 550 kWh | 7.10억 | 42.3년 |

### 규격 격자 — 살 수 있는 사양으로 낸다 (50세션 3장)

49세션까지 **123 kW / 120 kWh** 처럼 기성품에 없는 값이 나왔다. 도입 사례 여섯
건에서 관찰한 규격을 `data\ess_spec_grid.json` 에 두고 **올려 잡는다**.

    PCS      50 · 75 · 100 kW, 100 kW 초과는 병렬 50 kW 단위 (150 = 100+50)
    배터리   50 kWh 단위 (랙 100 kWh · 반 랙 50 kWh)

**내려 잡지 않는다** — 목표를 못 지킨다. 올리면 투자비가 늘어 회수기간이
길어지는데 그것이 정직한 방향이다.

**격자가 선택 자체를 바꾼다.** 샘플에서 5,170 kW 의 정격 119.6 kWh 가 150 kWh 로
올라가고 5,180 kW 의 85.2 kWh 는 100 kWh 로만 올라가, **더 얕은 쪽이 이겼다**
(33.6년 대 31.7년). 카드 기준 최적이 5,170 → 5,180 으로 옮겨 앉은 까닭이다.

**마진 조건은 격자에 올려 잡기 전의 값으로 잰다.** 「이 부하 모양이 애초에
회수될 수 있는가」 를 묻는 판정이라 조달 규격이 끼면 경계가 목표에 따라
오르내린다 — 얕은 목표의 방전시간이 격자 위에서 1.00h 로 튄다.

**최소 규격은 필요 출력에 건다** (`ess.min_pcs_power_kw`, 기본 50 kW). 격자로
올릴 수 있다 해도 8배 과설계(6.2 → 50 kW)는 조달이 아니라 억지다. 못 미치면
회수기간도 사양 표도 싣지 않고 필요 출력·용량·방전시간만 낸다
(`BELOW_MINIMUM_CONCLUSION`). C3 평탄형과 소형 사무빌딩이 이 자리다 — **부하가
평탄하면 큰 건물이라도 깎을 것이 몇 kW 뿐이다.**

**뭉친 줄은 합친다** (`ess_spec_groups`). 격자를 쓰면 목표 여럿이 한 사양으로
묶인다 — 샘플 21점이 15사양이다. 대표는 **그 사양이 버티는 가장 깊은 목표**다:
같은 설비를 샀으면 그것이 견디는 가장 낮은 목표로 돌리는 것이 맞고, 저감량·
절감액이 가장 크고 회수기간이 가장 짧은 줄이 자동으로 대표가 된다.

**「최소 규모」 표식을 없앴다.** 다섯 줄에 모두 붙어 **구별하는 힘이 없었고**
투자비도 다섯 줄이 같았다 — 모든 줄에 붙는 표식은 표식이 아니다.

### 단가 경로 셋 (50세션 3-5)

| | 경로 | 어디에 있나 |
|---|---|---|
| ① | **2항식** — 기본이고 계산에 쓰인다 | 기준 데이터 화면 |
| ② | **kWh 구간 단가** | 기준 데이터 화면 |
| ③ | **견적 총액** | ESS 카드 |

②의 기본값은 2항식을 **구간 중앙**에서 환산해 채운다 —
`tools\fit_ess_cost.py` 의 `capacity_bands`. 네 값(2,266,000 · 1,553,000 ·
1,196,000 · 993,000원/kWh)이 이 규칙에서 한 자리도 어긋나지 않고 나온다.
경계는 **상한 포함**이라 구간 저변에서 투자비를 비싸게 잡는다 — 회수기간이
길게 나오므로 안전한 방향이다.

**어느 경로로 계산했는지 결과에 한 줄로 표시한다** (`EssResult.pricing_path`).

**최소 규모는 정격 용량에 건다** (46세션 — 50세션에 격자가 대신한다). 카드는 `quote(정격)` 으로 거는데
곡선만 전달 용량에 걸어, 정격이 1.185배 큰 만큼 경계가 어긋나 있었다 —
자료 일곱 121점 중 1점(C5 목표 6,020 kW)에서 실제로 엇갈렸다. 맞추자 곡선과
카드의 **투자비가 정확히 같아졌고**(배율 1.0000), 개략 곡선이 고르는 자리도
카드 기준 최소와 일치했다 — C3 3,000→3,010, C5 5,940→5,960.

**용량 산정 기준은 '하루 최대 초과 에너지'다.** 충전 기회가 야간뿐이므로
연속 구간 최대로 잡으면 같은 날 초과가 두 번일 때 목표를 놓친다(샘플
5,200 kW 에서 실제로 놓쳤다). 기간 합계인 '총 초과 에너지'는 배터리 용량으로는
과대다(4,500 kW 목표에서 178 MWh).

**투자비는 조달 사례 회귀로 낸다** (13세션에 교체했다).

    설비비 = 106,925,000원 + 840,000원/kWh × 용량(kWh)   R² 0.99958 (옥외 관급 4건)
    투자비 = 설비비 + 전기공사비

계수는 `data/ess_cost_model.json` 에 있고 `tools/fit_ess_cost.py` 가 다시 맞춘다.
**코드에 손으로 적지 않는다.** 홀드아웃(한 건씩 빼고 예측) 오차는 1.0~2.5% 다.
계수는 **천 원 단위로 반올림**해 저장한다 (14세션) — 사례가 넷이라 그 아래 자리는
뜻이 없고, 반올림 재현 오차는 −0.85~+1.43% 로 사실상 달라지지 않는다.

**단가 입력은 2계수 방식이다** (14세션). kW당 단가로는 표현할 수 없다 — 같은
100 kW 인데 용량이 156.4 kWh 면 2.35억, 400 kWh 면 4.43억이다. 확장 패널에서
**고정비와 용량단가 둘만** 조정하고, 조정하면 「계수 조정됨」을 표시한다.
견적 총액 직접 입력 경로는 그대로 둔다.

- **단일 kWh당 단가로 표현하지 않는다.** 고정비가 1.07억으로 지배적이라
  총액÷용량이 50 kWh 440만원, 400 kWh 146만원으로 세 배 변한다.
- **kW 는 설명 변수가 아니다.** PCS 가 50·75·100 kW 로 흩어져 있는데도 kWh
  하나로 R² 가 0.999 를 넘는다.
- 전기공사는 옥외 기준 200 kWh 이하 6,300만~8,300만원, 400 kWh 약 1.41억원이다.
  실내 설치면 줄지만 근거가 한 건뿐이라 참고값이다.
- 적용 구간은 100~400 kWh 다. 아래는 100 kWh 로 올려 산정하고 알리며, 위는
  참고값으로 표시한다.

**핵심 산출물은 성립 조건이다.** 회수기간 하나로는 "왜 안 되는가" 를 알 수 없다.

    kW당 배터리비 = 용량단가 × 방전시간
    10년 절감/kW  = 기본요금단가 × 12 × 10
    마진/kW       = 절감 − 배터리비
    필요 저감량   = (설비 고정비 + 전기공사) ÷ 마진

기본요금 단가는 계약종별·전압·선택요금에서 가져온다. 샘플(목표 5,200 kW, 방전
0.44시간)에서는 필요 저감량 358 kW, 산출된 저감량 93 kW 다.

**판정 문장을 쓰지 않는다** (14세션). 「성립하지 않습니다」·「경제성 없음」 같은
단정 대신 두 값을 나란히 놓고 사실만 적는다 — 곡선이 근거이므로 판단은 사용자가
한다. LCOS 참고단가는 차익거래 에너지 단가와 2030년 전망 회수기간에만 남겼다.

차익거래 수익은 매 평일 한 사이클을 온전히 돌렸을 때의 잠재값이며 피크저감
절감액에 **합산하지 않는다.** 까닭이 셋이다 (41세션이 샘플을 실제로 돌려 확인했다).

**① 도구가 돌리지 않는 운전이다.** 디스패치는 목표를 넘을 때만 방전한다. 샘플
고른 목표(5,170 kW)에서 359일 중 **12일**만 방전해 연 **2.7 사이클**을 돈다 —
차익거래가 전제하는 평일 227 사이클과 **84배** 차이다.

**② 예비 규칙이 없다. 없이 돌리면 오히려 나빠진다.** 최대부하에 보이는 대로
방전하면 정작 피크가 왔을 때 배터리가 비어 피크를 못 깎는다. 샘플을 그렇게 돌리면
달성 피크가 5,170.0 → 5,248.6 kW 로 되밀리고 기본요금 절감이 542만원 줄어
**회수기간이 30.75 → 50.61년**이 된다. 그날 피크만큼 남겨 두면(완전 예지) 25.52년,
모델 잠재값의 88.6% 를 얻지만 **예지를 전제한 값은 산출물에 낼 수 없다.**

**③ 열화·수명이 계산에 없다.** 사이클이 84배가 되는 대가가 어디에도 없다.
`battery_life_years` 는 달력 수명이고 사이클 수명 모형은 없다.

26세션은 「피크컷 디스패치가 이미 일부를 실현해 이중 계산」 을 근거로 적었으나,
41세션이 그 겹침을 재 보니 **사이클 1.06% · 금액 0.80%** (케이스 여섯에서
0.46~1.85%) 로 사실상 없는 몫이었다. 겹침 비율은 화면에서 뺐다 —
**근거가 틀렸던 것이지 결론이 틀린 것은 아니다.**

차익거래를 반영하려면 **예지 없는 운전 전략을 먼저 정해야 한다.** 그때 고른 목표도
함께 옮겨간다 — 샘플 −10 kW(정격 +37%), C3 −40 kW(+305%), **C5 −430 kW(+472%)**
로 C5 는 40세션 정밀화의 창을 벗어난다.

#### 7.5-1 잉여 처리 {#tech-surplus}

**7.5 태양광 안에 있다** (41세션). 잉여는 태양광의 결과이지 개선안이 아니다 —
잉여가 0 이면 화면에 아무것도 그리지 않고, 태양광 카드의 「잉여 없는 최대 용량」
이 「생기려면 얼마가 필요한가」 에 답한다.

**상계거래 — 그 슬롯의 실제 계시로 그 달 사용량에서 차감한다.**
낮 시간을 일괄로 중간부하에 넣지 않는다. 여름·봄가을 15~21시와 겨울 09~12시는
최대부하이고 태양광이 그 시간에도 발전한다. 계시 판정은 요금 엔진
(`classify_slots`)의 결과를 그대로 쓰므로 요일 규칙(토요일 최대→중간,
일요일·공휴일 전량 경부하)도 자동으로 따라온다.

    차감 = min(그 달 그 계시 잉여 + 앞 달 이월, 그 달 그 계시 **순부하** 사용량)
    금액 = 차감 × 그 (달, 계시)의 실효 단가       ← 할인 특례가 섞이므로 금액/kWh 로 낸다
    이월 = 남은 몫 → 같은 계시로 다음 달

차감 한도를 **순부하**(태양광 자가소비를 뺀 뒤)에서 읽는 것이 요점이다. 원부하로
재면 태양광이 이미 지운 사용량까지 상계 여지로 세게 된다.

**설비 용량으로 구간이 갈린다** (`data\assumptions.json` 의
`surplus.offset.carry_only_max_kw` · `surplus.offset.max_kw`).

| 용량 | 처리 |
|---|---|
| 10 kW 이하 | 이월만 되고 현금 정산이 없다 |
| 10 kW 초과 ~ 1,000 kW | 당월 차감 뒤 기간 말 잔여를 SMP 로 정산 |
| 1,000 kW 초과 | 상계거래를 선택지에서 뺀다 |

판정은 화면에 설정된 kWp 로 한다. 규정은 모듈 정격과 인버터 용량 중 작은 값이
기준이지만 **초기 검토 도구이므로 인버터를 입력받지 않는다.**

**고른 시나리오는 절감액에 더한다** (48세션 · `with_surplus_revenue`). 41세션에
잉여를 태양광 안으로 옮기면서 자리만 옮기고 금액을 합치지 않아, 화면에 **더해지지
않는 두 수**가 남아 있었다 — 소형 사무빌딩 자료에서 절감액 2,543만원과 잉여 수익
241만원이고 회수기간 12.6년은 앞의 것만 본 값이었다. 더하면 11.5년이다.

    안 골랐다        더하지 않는다 (라디오는 기본값이 없다 — 41세션 2-2)
    골랐다           그 시나리오의 수익만 더한다. 셋을 비교하는 값이 아니다
    금액을 못 낸다    이름만 남기고 더하지 않는다 (단가를 지어내지 않는다)

**이중 계상이 아니다.** `apply_generation` 이 순부하를 0 에서 자르므로 역송분은
요금 계산에서 아예 빠져 있고, 상계 차감은 그 뒤에 남은 **순부하** 사용량을
한도로 잰다. 겹치는 몫이 없다.

**3단계 합산효과에도 들어간다** (`CombinationSpec.surplus_revenue_won`). 14세션은
「경제성DR·잉여 활용은 합산효과에 넣지 않는다」 고 정했는데, 그것은 잉여가 **독립
개선안(7.7)** 이던 시절의 결정이다 — 41세션에 전제가 사라졌다. **차익거래는 계속
뺀다**: 그날 피크에 쓸 몫을 남기는 운전 규칙이 없어 매 평일 한 사이클은 상한이지
예상값이 아니다.

**기본요금은 바뀌지 않는다.** 잉여는 부하가 낮은 시각에 나므로 요금적용전력과
무관하고, 태양광이 피크를 낮춘 효과는 이미 7.5 의 절감액에 들어 있다. 전력량요금만
다시 계산한다.

**단가를 지어내지 않는다.** SMP 단가가 없으면 잔여 kWh 만 내고 금액은 「미산출」,
잉여 판매 단가가 없으면 외부 판매 금액을 내지 않는다. SMP 단가는 하나로 적용하며
기간 길이를 구분하지 않는다. **자격요건은 판정하지 않는다.**

**단가에 기본값이 있다** (58세션 · `assumptions.json`).

    surplus.offset.smp_price_won_per_kwh     120.0   판단값
    surplus.external.price_won_per_kwh       140.0   판단값

**법령 유래가 아니므로 `rules_kr.json` 에 두지 않는다.** 시장 통용 수준의 참고값이고,
기준 데이터 화면에서 [판단] 배지로 고친다 — 화면에 손으로 배선한 칸이 아니라
`describe_items()` 가 내는 줄이다. **출고층(`data\defaults`)에도 함께 넣는다**
(57세션에 판단값 11건이 빠져 「출고값 복원」 이 앱을 죽인 자리다).

읽는 자리는 하나다 — `ui.state.surplus_prices()`. 태양광 카드·조합 비교·산출물
재료가 이 함수를 부른다. 세션에 위젯 값이 **없으면** 기준 데이터 기본값이고,
**있으면** `measure_float` 그대로다 (0 → `None` → 미산출). 위젯을 아직 그리지 않은
상태를 가르는 것이 `measure_price` 의 존재 이유다 — 상계거래를 고르면 외부 판매
단가 칸이 안 그려지는데 그렇다고 그 시나리오를 미산출로 둘 이유가 없다.

**적용 단가를 산출물에 적는다.** `SurplusResult.applied_price_note` 하나가
문장을 짓고 넷이 그것을 쓴다.

| 자리 | 어떻게 |
|---|---|
| 화면 | 잉여 처리 절의 캡션 (툴팁에서는 뺀다 — 같은 문장이 한 절에 두 번 서지 않게) |
| PPT | `SurplusPage.note` 에 이어 붙는다. `slides.py` 는 고치지 않았다 |
| Excel | 「수단별 결과」 의 `└ 잉여` 줄 비고 |
| Word | 부록 A 태양광 계산 근거 (`basis` 등급 안내 `surplus.applied_price`) |

**적용하지 않은 단가는 문장에서 빠진다.** 현금 정산 구간이 아니면 SMP 단가가
`None` 이라 그 조각이 서지 않고, **잉여가 0 이면 문장 자체가 없다.**

`SURPLUS_PAGE_NOTE` 에서 「외부 판매는 단가를 입력해야 산출됩니다」 를 뺐다 —
기본값이 생겨 늘 참이 아니고, 비웠을 때는 시나리오 표의 비고가 그 자리에서 말한다.

**일별 잉여 그림은 화면에만 있다** (41세션). 수단 장은 그림 둘까지이고(38세션
3절 — 셋을 넣으면 축 눈금이 뭉개진다) 태양광 장은 연간 발전량과 대표일 곡선이
그 둘을 이미 쓴다. 보고서에는 잉여량·자가소비량과 시나리오 한 줄이 7.5 장에
녹아 들어간다.

### 4.4 조합 재계산 — 왜 단순 합이 아닌가 {#tech-combination}

**수단별 절감액을 더하면 틀린다.** 수단이 서로의 전제를 바꾸기 때문이다.

| 상호작용 | 무슨 일이 일어나나 |
|---|---|
| 요금제 → 다른 수단 | 기준 단가가 바뀌어 계약전력·역률·ESS 절감액이 달라진다 |
| 태양광 → 선택요금 | 사용량이 줄면 **최적 선택요금이 바뀐다.** 기본요금 비중이 커지므로 |
| 태양광 → 역률 | 유효전력이 줄어 역률이 나빠진다. 기본요금에 추가가 붙는다 |
| ESS → 기본요금 | 피크를 낮추면 기본요금 기반 자체가 달라진다 |
| 태양광·ESS → 역률 감액 | 역률 감액은 기본요금에 비례한다. 기본요금이 줄면 감액도 준다 |
| 계약전력 → 하한 | 계약전력을 낮추면 요금적용전력 하한이 함께 내려간다 |

그래서 조합마다 **부하를 처음부터 다시 만들어** 요금을 한 번 계산한다.

```
부하 → apply_generation(PV) → dispatch_peak_shaving(ESS) → calculate_bill()
```

**역률도 조합에 넣는다** (14세션). 역률은 부하를 바꾸지 않고 기본요금 조정액만
바꾸므로 `BillingOptions.power_factor_pct` 로 얹는다. 넣지 않으면 위 표의 다섯째
줄(기본요금이 줄면 역률 감액도 준다)이 보이지 않는다.

**3단계는 세 부분이다** (14세션 5절).

| 부분 | 무엇을 | 어디서 |
|---|---|---|
| ① 개선안별 요약 | 독립 평가 결과 **그대로**. 재계산 금지 | `report.standalone` |
| ② 합산효과 | 조합 재계산 + **단순 합과의 차이** | `compare.combination` |
| ③ 조합 비교 | 조합을 쌓아 올려 비교한다 | `compare.combination` |

②의 **차이**가 3단계의 존재 이유다. 차이가 생긴 이유는 위 표에서 **실제로 발생한
것만** 골라 적는다 — 해당 없는 줄을 적으면 없는 상호작용을 만들어낸다.

**계약전력 추가 하향 판정은 ②에서만 낸다.** 2단계 7.2 카드는 현재 부하 기준이라
다른 수단을 켜도 값이 바뀌지 않는다 (독립 평가). 조합 부하 기준의 여지는
`evaluate_contract_adjustment(usage, combined.bill, ...)` 로 따로 계산한다.

> **「고를 수 있는 목표가 없다」 는 갈래가 둘이다** (54세션). 곡선에 마진 조건을
> 넘는 점이 아예 없는 경우(48세션)와, 창을 넓혀 훑었는데도 **값이 매겨지고
> 목표를 지키고 마진이 있는 점**이 하나도 없는 경우다. 둘 다 `viable=False` 이고
> `target_kw` 는 0 이다 — 뒤쪽이 `viable` 을 넘기지 않아 기본값 참이 그대로
> 나갔고, 3단계가 그 목표로 ESS 를 만들어 **절감액이 음수인 카드**와 회수기간이
> 「—」 인 줄에 「최단 회수기간」 표식이 붙은 표가 나왔다.


> **기본요금이 계약전력에 붙는 종별은 애초에 성립할 수가 없다** (56세션 ·
> 61세션에 범위를 좁혔다). 요금적용전력에 붙으면 피크를 낮추는 만큼 주는데,
> **계약전력**에 붙으면 아무리 깎아도 그대로다 (약관 제68조 제2항).
> **갑Ⅱ 는 여기 들지 않는다** — 저압이 없어 요금적용전력 기준이다.
> 갑Ⅰ·교육용(갑)은 전력량요금까지
> **단일 단가**라 충·방전 차익도 0 이고 왕복손실만 남아 **절감액이 음수**가 된다.
> 개략 곡선(`ess_target_curve`)은 그 사실을 모르고 `저감량 × 기본요금단가` 로
> 회수기간을 내므로 「성립하는 목표」 를 만들어 낸다 — **훑기 전에 끊는다.**

**경제성DR·잉여 처리는 ②에 넣지 않는다.** 요금이 아니라 별도 정산·수익이라 조합
부하에 얹을 수 없다. ①에는 그대로 있고, ②는 그 사실을 적는다 — 같은 것을 비교
하지 않으면 「차이」가 뜻을 잃는다.

**조합 확실성은 가장 낮은 구성 요소를 따른다.** 태양광과 ESS 를 함께 넣으면
조합 전체가 ESS 등급이다. 표에서 등급을 섞어 보여주면 의사결정이 흐려진다.

**등급은 어디에도 없다** (28세션 화면 · **53세션 산출물**). 무엇에 대한
확실성인지가 이름에 없어 「높음」 이 어느 정도의 믿음인지 가늠할 수 없었고,
잉여가 0 이라 수익 0원이 확정인 줄에도 「중간~낮음」 이 붙었다. 등급이 보증도
아니다. 28세션에 화면에서 뺐는데 **PPT·Excel·Word 에만 남아** 있었다 — 화면과
산출물이 다른 것을 보여 주면 나란히 놓았을 때 어느 쪽을 믿을지 알 수 없다.

**계산과 데이터는 남긴다.** `~kwise.measures.Certainty` · `lowest_certainty` ·
각 결과의 `.certainty` 가 그대로 있으므로 되살릴 때 **열만 되돌리면 된다.**
「조합의 등급은 가장 낮은 구성 요소를 따른다」 는 근거 줄은 가리킬 대상이
없어져 만드는 자리에서 지웠다 (`combination.certainty_rule`).

**켠 수단만 조합에 들어간다.** 켜지 않은 수단이 섞이면 "보지 않은 것"이
"검토했더니 이만큼"으로 둔갑한다. 반대로 조용히 빼면 "효과가 없었다"로 읽히므로
「검토 범위」로 명시한다.

### 4.5 감도 — `sharpen()` {#tech-sensitivity}

발전량 예측은 **총량은 실측과 부합하나 피크 발전량을 과소 산출하는 경향**이
있다 (재분석 데이터의 평탄화 편향). 그래서 흔드는 축은 총량이 아니라
**정오의 첨예도**다.

```
adjusted(t) = 일평균발전 + (기준(t) − 일평균발전) × s
```

**일별 총량이 보존된다.** 발전이 있는 슬롯만의 일평균을 쓴다 — 야간 0 을
넣으면 밤의 편차가 전체를 지배한다. `s = 1.0` 이면 **원본을 그대로 돌려준다**
(부동소수 오차조차 만들지 않는다). 기준 시나리오가 시뮬레이션 결과와 완전히
같아야 회귀값이 흔들리지 않는다.

`sharpen` 은 양의 상수배에 **동차**이므로 단위 프로파일에 한 번 걸고 용량을
곱한 것과 용량을 곱한 뒤 조정한 것이 같다. 20단계마다 다시 계산할 이유가 없다.

| 시나리오 | s | 뜻 |
|---|---|---|
| 평탄형 | 0.85 | 정오가 덜 뾰족하고 어깨가 두껍다 |
| 기준 | 1.00 | 시뮬레이션 그대로 |
| 첨예형 | 1.25 | 정오가 뾰족하고 어깨가 얇다 |

#### 상한이 고정되지 않는 이유 {#tech-sensitivity-range}

**'첨예형'은 좋은 값이 아니다.** 총량이 보존되므로 첨예도를 올리면 정오가
높아지는 대신 **아침·저녁 어깨가 낮아지는데, 피크 저감은 어깨 출력에 걸린다.**
부하 피크가 정오에 정확히 있지 않으면 첨예형이 오히려 불리하다.

케이스 스터디 6종 × 3용량 = **18개 조합에서 기본요금 절감액의 상한 시나리오는
평탄형 16건, 기준 2건, 첨예형 0건**이었다.

그래서 결과를 **범위로 표시한다.**

```
기본요금 절감  3,152만원 (프로파일 감도 범위 2,897 ~ 3,266만원)
```

세 값을 나란히 놓으면 읽는 사람이 "어느 쪽이 좋은 값인가"를 찾게 되는데 이
축에는 좋고 나쁨이 없다. 최댓값·최솟값은 `min`/`max` 로 뽑고 **어느 시나리오가
상한인지 고정하지 않는다.** 원자료 3행은 근거표로 별도 시트에 둔다.

**요금제 전환·계약전력 조정·역률 개선에는 감도를 적용하지 않는다** — 실측
데이터와 요금표·약관만으로 확정되는 계산이다. 확률 표기(P90 등)는 쓰지 않는다.
부하가 1년 실측 고정이라 통계적으로 부정확하다.

#### 화면에서 뺀 이유 (28세션) {#tech-sensitivity-offscreen}

계산은 그대로 돌고 결과는 Excel 두 시트와 보고서에 실린다. **화면 표기만
없앴다.** 세 가지를 재어 보고 내린 판정이다.

| 지표 | 기준값 | 감도 폭 |
|---|---|---|
| 기본요금 절감액 | 2,320만원 | **±15%** — 감도가 뜻을 갖는 유일한 지표다 |
| 전력량요금 절감액 | 2억 5,026만원 | 0.3% (총량 보존) |
| 총 절감액 | 2억 7,845만원 | **1.3%** — 결론이 움직이지 않는다 |
| 회수기간 | 7.8년 | 7.8 ~ 8.0년 |

**그리고 목록의 분해 지표 둘은 감도와 무관한 크기였다.** 「기본요금 절감액」·
「전력량요금 절감액」은 **조합 전체(요금제 전환 포함)의 기준선 대비 값**이라,
현행이 선택Ⅰ이고 조합이 선택Ⅱ로 갈아타면 전력량요금 절감이 1억을 넘고 기본요금
절감은 음수가 된다 (선택요금이 둘을 맞바꾸는 제도다). 감도 폭 0.03% 짜리
숫자가 감도 이름 아래에 억 단위로 놓이면, 읽는
사람은 그것을 다른 화면의 수단별 값과 비교하게 된다. 두 값의 합이 총 절감액과
다른 것도 이 자리에서는 설명할 수 없다 (역률요금 몫이 어느 쪽에도 없다).

### 4.6 안내 체계 — 등급 넷과 사실 ID {#tech-notices}

**같은 문구를 두 번 내지 않고, 화면에서 뺀 것은 반드시 산출물에 있다.**

안내는 :class:`Notice` 하나다. 문구를 만드는 **발신처가 등급과 사실 ID 를 함께
붙인다** — 받는 쪽이 문구를 훑어 짐작하지 않는다.

| 등급 | 뜻 | 화면 | 보고서 |
|---|---|---|---|
| 차단(BLOCK) | 계산이 안 됨 | 본문 · 색 | 본문 |
| 주의(WARN) | 결과 해석이 달라짐 | 본문 · 아이콘 | 본문 |
| 근거(BASIS) | 이 숫자가 어디서 왔나 | **툴팁** | 본문 · 부록 A |
| 참고(INFO) | 전제·한계·제도 | **없음** | 부록 C |

**사실 ID 가 중복을 가른다** (`모듈.사실`, 여럿이면 `모듈.사실:판별자`).
문구가 아니라 ID 로 비교하므로 두 모듈이 같은 사실을 조금 다르게 적어도 한 번만
나간다. 같은 사실이 여러 벌일 때(월별 결측률·정전 구간·조합)는 판별자로 가른다.

```
ess.charge_new_peak            measures\ess.py 와 compare\combination.py 가 함께 쓴다
quality.month_missing_rate:2023-11   달이 판별자다
```

**앞말은 표시할 때만 붙인다** (`prefixed`). 조합명을 문구에 심으면 그 앞말이
중복 판정에 걸려 같은 조합의 다른 경고가 통째로 사라진다.

18세션까지 쓰던 **부분 문자열 등급 추정은 21세션에 지웠다.** ``fact`` 는 필수라
빠뜨리면 mypy 가 잡는다. `tools\notice_audit.py` 가 실주행으로 한 번 더 센다.

#### 문구가 사실과 어긋나는 두 자리 {#tech-notice-truth}

31세션에 같은 병을 두 군데에서 잡았다. **둘 다 「0」 이 원인이다.**

    경계     `<=` 로 **기준과 같은 값**을 미달 쪽에 넣었다
             → 역률 92.0%(약관 제42조 간주값)가 「0.0%p 미달」 로 나갔다
    반올림   0 이 아닌 값이 `.1f` 로 **0.0 으로 찍혔다**
             → 91.96% 는 진짜 미달인데 폭이 안 보였다

간주값이 하필 기준과 같은 92% 라, **역률을 손대지 않은 자료가 전부 그 문구를
받았다.** Excel 의 역률요금 줄도 같은 병이었다 — 0 원인데 「추가」 라고 적었다.

고치는 법도 둘이다. 경계는 **세 갈래로 가른다** (충족·미달·초과) — 어느 갈래가
어떤 말이 되는지는 그 자리의 제도 지식이라 문구를 만드는 쪽이 정한다. 반올림은
`kwise.magnitude.magnitude()` 가 **보일 때까지 자릿수를 늘린다.**

`kwise.money` 와 반대 방향인 것에 주의한다 — 금액은 **일부러 굵게 절사**한다
(천 원 단위). 크기가 곧 뜻인 자리와 금액이 뜻인 자리는 규칙이 다르므로 두 모듈을
합치지 않는다.

### 4.7 계산 근거 — 산식과 대입값 {#tech-worksheet}

카드마다 **접힌 「계산 근거」** 가 있다. 산식과 그 자리에 넣은 값을 같은 줄에
둔 표 하나다 (`kwise.report.worksheet`).

```
기본요금   5,293.4 kW × 8,320 원/kW × 12.00개월   521,823,000원
전력량요금  계절·시간대별 단가 × 사용량
  경부하                              8,871,534 kWh
  소계                              2,775,718,000원
합계                                3,297,542,000원
```

**LaTeX 을 쓰지 않는다.** 화면(Streamlit)·Excel·Word 셋이 같은 표를 써야 하므로
구분·산식·값 세 열로 낸다. 만드는 함수가 하나이므로 세 산출물이 갈라질 수 없다.

**여기서 다시 계산하지 않는다.** 이미 나온 결과 객체의 값을 배치할 뿐이다 —
산식을 다시 적으면 화면의 숫자와 근거의 숫자가 갈라진다.

**화면 예산.** 카드·절마다 본문 3줄 · 확인사항 3항목이 한도다 (값은
`assumptions.json` 의 `ui.body_line_budget`·`ui.notice_budget`). 접힘과 툴팁은
한도 밖이다 — 펼치지 않아도 눈에 들어오는 글만 센다.
``tools\screen_budget.py`` 와 시험이 **같은 함수**로 잰다.

### 4.8 그래프 규약 {#tech-charts}

**화면(altair)과 보고서(png)가 같은 규약을 쓴다.** 한쪽만 고치면 두 그림을
나란히 놓고서야 어긋난 것이 드러난다 (13세션에 겪었다).

| 규약 | 화면 | 보고서 |
|---|---|---|
| 범례 자리 | `charts.LEGEND` — 바깥 오른쪽 | `figures.LEGEND_STYLE` — `bbox_to_anchor=(1.01, 1.0)` |
| 범례 배경 | 칠하지 않는다 (`fillColor=None`) | `frameon=False` |
| 축 자르기 | `charts._CUT_SCALE` | `set_ylim` |
| 피크 확대 창 | `frames.PEAK_ZOOM_HOURS` · `frames.peak_window()` (**공유**) | 〃 |

**범례 배경을 칠하지 않는 이유.** 17세션이 `fillColor="white"` 를 주었는데,
라이트 모드에서는 배경과 같아 티가 나지 않았지만 **다크 모드에서 흰 상자에
회색 글씨**가 되어 읽히지 않았다. 색을 고정하지 않고 테마가 칠하게 둔다.

**바깥 오른쪽 범례는 그림 오른쪽 «위»에서부터 쌓인다** (27세션). 도형 옆에
설명을 직접 적는 차트(전력삼각형)는 그 글자가 꼭짓점에서 오른쪽으로 뻗어 같은
자리를 다툰다 — 규약이 적용되지 않은 것이 아니라 **적용된 규약이 그 그림에서만
부딪히는 것**이다. `charts.LEGEND_BELOW`(아래·가로)를 그 차트에만 쓰고, 나머지
셋(배경 없음·안쪽 금지·글자색 고정 금지)은 예외 없이 지킨다. 시험이 예외 목록
(`LEGEND_BELOW_CHARTS`)을 못 박는다.

**같은 병이 막대 끝 글자에도 있었다.** 현행 대비 차액 차트는 값이 모두 음수이면
0 이 그림의 오른쪽 끝이라 「현행」 글자가 그림 밖으로 나가 범례 위에 겹쳤다.
축 범위를 글자 폭만큼 넓혀 **그림을 왼쪽으로 줄였다** — mark_text 는 레이아웃
계산에 들어가지 않으므로, 자리를 비워 주지 않으면 언제든 밖으로 나간다.

**선·면은 자르고 막대는 자르지 않는다.** 선은 두 값의 *간격*이 뜻이라 축을
자르면 그 간격이 드러난다. 막대는 *길이*가 곧 값이라 자르면 길이가 거짓말을
하고, 개수를 세는 막대(상위 구간 수)와 부호를 가르는 막대(충전＋·방전−)는 0 이
기준점 그 자체다. **축 제목에 「0 부터 시작하지 않습니다」 를 적지 않는다**
(21세션) — 눈금을 보면 안다.

**칸 폭을 적지 않으면 실오라기가 된다** (32세션). vega-lite 는 폭을 주지 않은
띠 축의 칸을 **20px** 로 잡고 streamlit 테마가 그 85%를 막대로 쓴다 — 17px 짜리
누적 막대에서는 조각 넷 가운데 작은 것이 선으로 보인다. 월별 요금 구성은
`charts.MONTH_BAR_STEP`(60px)으로 칸을 못 박아 막대를 51px 로 만들고, 간격은
비율을 그대로 두어 함께 넓어진다(3px → 9px). 달이 많은 자료는
`charts._month_step()` 이 칸을 줄여 가로 스크롤을 막는다.

**다만 그 값은 하한이다.** 화면 폭에 맞춰 늘어나는 경로(`width="stretch"`)에서는
프런트엔드가 spec 의 `width` 를 **화면 폭으로 덮어쓴다** — 그림 폭을 우리가 정할
수 없으면 막대 두께도 정할 수 없다. **막대 두께로 무엇을 말하려 들지 않는다.**

**비중을 비교하는 그림은 원이다** (33세션 → 34세션에 자리 이동). 33세션이 원을
월별 요금 구성에 붙였는데 지시가 잘못 전달된 것이었고, 제자리는 **계시별 사용량
구성**이다 (`charts.band_donut_chart`). 요금 구성은 달마다의 높이를 비교하는
그림이라 막대가 맞다.

| 그림 | 무엇을 비교하나 | 모양 |
|---|---|---|
| 월별 요금 구성 | 달마다의 **높이** | 누적 막대 |
| 계시별 사용량 구성 | 계절마다의 **비중** | 도넛 넷 (탭 없이 한 줄) |

도넛은 `charts._donut()` 하나로 그린다 — 각·조각 순서·라벨 규칙이 한 곳에 있어야
그림이 늘어도 갈리지 않는다. **범례를 달지 않는다**: 원이 넷이라 범례를 달면
같은 이름 넷이 네 번 실리고, 조각 위 라벨이면 한 번이다.

**제목을 vega 에 두지 않는다** (35세션). 34세션에 `TitleParams` 로 계절 이름과
합계를 얹었더니 **제목 윗부분이 잘렸다** — 층(layer) 차트의 제목은 높이 계산에
들어가지 않는 경우가 있다. 그리고 부제는 vega 기본색(검정)이라 **다크 모드에서
배경에 묻혔다.** 둘 다 Streamlit 캡션으로 그림 **위에** 두면 없어진다 — 잘릴
자리가 없고 글자색이 테마를 따른다.

**캡션이지 본문이 아니다.** 넷을 `st.markdown` 으로 적으면 그 자리의 본문 예산
(3줄)을 그림 이름 넷이 통째로 먹는다 — 캡션은 예산 밖이다 (`screen_budget`).

**좁은 칸에서는 라벨이 조각을 파고든다.** 넷이 한 줄이라 칸 하나가 화면 폭의
4분의 1 이다. 34세션의 반지름(78px)은 라벨이 놓일 자리를 남기지 않았다 —
62px 로 줄이고 라벨을 바깥 +24px 로 밀었다.

**17세션 축 규약은 막대에 대한 것이다.** 원에는 축이 없어 「자르지 않는다」 가
성립하지 않는다 — 규약을 고칠 일이 아니라 **해당 없음**이다. 대신 각이 곧
비중이므로 `theta` 를 쌓아(`stack=True`) 같은 뜻을 지킨다.

**글자색 규약** (23세션 → 35세션에 넓혔다).

| | |
|---|---|
| **중립색(흰·회·검)을 글자에 박지 않는다** | 한쪽 모드가 반드시 깨진다. 테마가 칠하게 두거나 Streamlit 텍스트로 뺀다 |
| **채색은 허용한다** | 그 글자가 어느 선의 것인지 색이 말해 준다 (30세션 축 제목 규약) |
| 다만 **중간 명도**여야 한다 | 어두운 남색(`#08519c`)은 검은 바탕에서 선도 축 제목도 가라앉았다 — 35세션에 `#3182bd` 로 올렸다 |

시험이 `charts.py` 의 `mark_text` · `titleColor` 줄을 훑어 중립색이 박혔는지 본다.

**두 축짜리 그림의 기준선은 그 축의 층 안에 둔다** (32세션). 기온 그림은
`resolve_scale(y="independent")` 라, 평균 기준선을 바깥 층에 따로 두면 vega 가
그 선에도 제 축을 만들어 주어 곡선과 다른 높이에 그린다. 기온 선·기준선·라벨을
한 층으로 묶어 축 하나를 함께 쓴다. **값은 선 위 라벨로 적고 범례를 늘리지
않는다** — 이름은 관측 기간이 정한다(`frames.temperature_mean_frame()`).

**층 안에서 축은 하나로 합쳐진다** (33세션). 32세션에 기준선·라벨에 `axis=None`
을 주었더니 vega 가 y 축을 합칠 때 **null 이 이겨 오른쪽 눈금이 통째로 사라졌다**
— 기온 곡선은 그려지는데 범위와 단위(℃)를 읽을 수 없었다. 세 층이 `charts._temp_y()`
하나로 **똑같은 축 정의**를 쓴다. 합칠 것이 하나뿐이면 다툴 일이 없다.

**날짜 표기는 한 벌뿐이다** (33세션). vega 의 기본 로케일이 영어라 축에 `May` ·
`Apr 30` 이 찍혔고, vega-lite **spec 에는 로케일을 실을 수 없다** (vega-embed
옵션이라 streamlit 을 거쳐 넘길 길이 없다). 차트마다 `format` 을 적으면 다음에
새 차트가 또 영어로 나오므로, 라벨 식 한 벌을 날짜 축 전부가 쓴다.

| 자리 | 무엇 | 어디 |
|---|---|---|
| 날짜 축 눈금 | 1월 1일 「2024년」 · 달의 첫날 「5월」 · 그 밖 「4월 30일」 | `charts.DATE_LABEL_EXPR` · `charts.date_axis()` |
| 날짜 툴팁 | 「2024년 4월 30일」 — 줄여 적지 않는다 | `charts.DATE_FORMAT` · `charts.date_tooltip()` |
| 하루 안 축 | 「09:15」. 날짜는 그림 제목이 적는다 | `charts.TIME_FORMAT` · `charts.time_axis()` |
| 하루 안 툴팁 | 「4월 30일 09:15」 | `charts.TIME_TOOLTIP_FORMAT` · `charts.time_tooltip()` |
| 달 축 (띠) | 「2023년 4월」 · 「5월」 — **해는 바뀔 때만** | `frames.month_labels()` |
| 보고서 png | 같은 규칙. `%-m` 을 Windows 가 모르므로 직접 만든다 | `figures.korean_date_label()` · `figures.date_axis()` |
| Excel | **바꾸지 않는다.** ISO 서식(`YYYY-MM-DD HH:MM:SS`)과 `2023-04` 는 로케일을 타지 않고 정렬·재계산에 쓰인다 | — |

시험이 **화면에 그려진 스펙**을 훑어 날짜 축이 규약을 탔는지, 영문 달 이름이
남았는지 본다 (`test_모든_날짜_축이_한국식이다`).

**그림마다 물음표를 단다** (`text.CHART_TIPS`). 지표 툴팁이 「산식 한 줄 + 의미
한 줄」인 것과 달리 그림에는 나눌 산식이 없어 **「무엇을 그렸나 + 무엇을 읽나」**
로 적고, 열쇠를 `chart.` 로 시작해 지표 툴팁과 가른다.

**목록 기호는 항목이 둘 이상일 때만 붙인다** (35세션). 한 문장 앞의 점은
「목록의 첫 줄」 처럼 보여 뒤에 무엇이 더 있는 줄 알고 찾게 된다. 둘 이상이면
붙인다 — 좁은 툴팁에서 문장이 줄바꿈으로 접히면 어디서 한 항목이 끝나는지 점
말고는 알 길이 없다. 규칙은 `text.bullet_list()` 한 곳에 있고 툴팁·기준 데이터
경고·검증 실패 셋이 그것을 쓴다.

**참고(`·`)와 주의(`⚠`)는 목록 기호가 아니다.** 그것은 **등급 표시**라 항목이
하나여도 남는다 (15세션 4절) — 무엇이 결론이고 무엇이 곁말인지 가르는 표시다.

### 4.9 예외 처리 기준 {#tech-exceptions}

**"모르는 것을 모른다고 표시한다"가 이 절의 전부다.**

| 상황 | 처리 | 하지 않는 것 |
|---|---|---|
| **결측** | 미보간. 계산에서 제외하고 결측률을 표시. 5% 초과 월은 관측·보정 두 기준 병기 | 보간, 0 채우기 |
| **정전** | 흔적 3종 중 **연속 결측을 뺀 나머지 2개 이상**이면 정전. 편중 판정에서 분자·분모 양쪽에서 제외 | 연속 결측만으로 정전 판정 |
| **그리드 이탈 행** | kW 산정에서 제외, **kWh 합계에는 포함**. 수단을 적용해도 건드리지 않는다 | 평균 환산 (43.2 kWh ÷ 14분 = 185 kW 로 왜곡된다) |
| **단가 미입력** | 투자비 `None` + **사유**. 회수기간도 미산출 | 0원 (→ "즉시 회수"로 읽힌다) |
| **하한 비율 없음** | 목표도 금액도 내지 않고 미산출 | 30% 가정 |
| **기상 취득 실패** | 캐시 → API → 사전 취득분 순, 셋 다 없으면 **중단하고 안내** | 인접 격자 대체, 0 으로 계산 |
| **계약전력 기준 종별에 계약전력 없음** | 예외를 던져 멈춘다 | 요금적용전력으로 대체 |
| **기준 데이터 파일 손상** | 최근 백업 → 출고값 순 복구 후 **반드시 알린다** (`recovered_from`) | 조용한 복구 |
| **기준 데이터 없음** | `RuleDataError` 로 멈춘다 | 코드 기본값 사용 |

**정전 판정에서 연속 결측을 흔적으로 세지 않는 이유.** 연속 결측은 모든
결측이 갖는 성질이라 정전의 근거가 못 된다. 이 조건 덕분에 샘플의 11월 통신
장애(930슬롯, 9.69일)가 정전으로 오인되지 않는다.

**최장 연속 결측을 편중 배수와 별도로 낸다.** 며칠짜리 공백은 시간대가 균등하게
빠져 배수가 1 근처가 되지만, 그 달의 최대수요 판정 자체를 무의미하게 만든다.

### 4.10 외부 인터페이스 — Open-Meteo {#tech-weather}

기상은 **Open-Meteo Archive API** (ERA5 재분석) 하나뿐이다. CC BY 4.0.

| 항목 | 값 |
|---|---|
| 변수 | `shortwave_radiation` `direct_normal_irradiance` `diffuse_radiation` `temperature_2m` `wind_speed_10m` |
| 해상도 | 시간별. ERA5 격자 25~31 km |
| 캐시 키 | **0.25° 격자로 반올림.** 시군구든 좌표 입력이든 같은 격자면 공유 |
| 재시도 | 429·5xx·연결 실패에 지수 백오프 (최대 5회, 2초 → 120초) |
| 호출 간격 | 최소 1초 (`Pacer`). 429 를 맞고 백오프하는 것보다 빠르다 |
| 폴백 | Windows PowerShell 경유. 프록시 뒤에서 Python HTTPS 만 막히는 사례가 있다 |

**조회 순서를 바꾸지 않는다.**

```
① PROJECT_CACHE 캐시   반복 호출을 여기서 막는다
② Open-Meteo API       성공분은 ①에 캐시한다
③ 사전 취득분          **폴백했다는 사실을 결과에 표시한다**
④ 둘 다 없으면 중단    0 으로 계산하거나 인접 격자로 대체하지 않는다
```

**시군구 단위 선택으로 충분하다.** ERA5 격자가 25~31 km 인데 서울 25개 구의
좌표 폭이 남북 20.6 · 동서 29.0 km 다. 같은 셀을 조회하므로 정확도를
희생하지 않는다. 좌표 직접 입력은 산악·해안 지형용 옵션으로 남긴다.

**Open-Meteo 라벨 규약은 미확정이다.** 라벨이 구간 시작이라는 전제로 대표
순시각을 라벨 + 30분으로 두었다. 실측 발전 데이터를 얻으면 발전 곡선이 통째로
30분 밀렸는지 대조한다. `WeatherLabel` 로 바꿔 끼울 수 있다.

### 4.11 PPT 보고서와 디자인 가이드 {#tech-slides}

**색과 크기가 오는 자리는 하나다** — `data\ppt_design.json` 이다.
`report.design.load_design_guide()` 가 읽고 슬라이드(`report.slides`)와 보고서
그림(`report.figures`)이 함께 쓴다. 코드에 기본값을 두지 않는 것은 기준 데이터
(`rules_kr.json`)와 같은 이유다 — 파일을 고쳐도 반영되지 않는 사고를 막는다.
시험이 두 모듈에 16진 색 리터럴이 있는지 훑는다.

| 무엇 | 자리 |
|---|---|
| 뼈대 (16:9 · 여백 0.5in · 블록 사이 0.3~0.4in · 텍스트 여유 10%) | `slide` |
| 글꼴 후보와 물러설 곳 | `font` |
| 크기 위계 (표지 46 / 제목 30 / 카드 21 / 본문 15 / 캡션 11.5pt) | `type_scale` |
| 슬라이드 색 (딥그린·다크·코랄·블루) | `colors` |
| png 팔레트 | `chart` |

**글꼴 이름을 `src\` 안에 두지 않는다.** OS 전용 이름은 그 OS 밖에서 깨지므로
배포 시험(`test_deployment.py`)이 `src\` 를 훑어 막는다. 설정 파일은 고쳐
끼울 수 있으므로 자리가 다르다. pptx 에는 **이름만** 적고 그리는 것은 읽는
사람의 PowerPoint 다 — Word 와 같다. 후보가 비면 `fallback` 으로 물러선다.

**한글에는 `a:ea` 를 따로 적어야 한다.** `a:latin` 만 있으면 PowerPoint 가 한글에
그 글꼴을 쓰지 않는다 (Word 의 `w:eastAsia` 와 같은 자리다).

#### png 글자색 규약은 화면과 다르다

35세션이 화면(altair)에 못 박은 것은 **「글자에 중립색(흰·회·검)을 박지
않는다」** 였다. 화면이 다크 모드를 타서 한쪽 모드가 반드시 깨지기 때문이다.

**png 에는 그 규약이 그대로 적용되지 않는다.** 배경이 흰색 하나로 확정이라
「어느 모드에서 깨지나」 라는 물음이 서지 않고, 오히려 어두운 중립색이라야
읽힌다. 대신 그 확정을 지키는 규약이 png 쪽에 따로 선다.

| | 화면 (altair) | 보고서 png |
|---|---|---|
| 배경 | 테마가 정한다 (라이트·다크) | **흰색 확정** — `render_png` 가 `facecolor` 를 준다 |
| 글자색 | **중립색을 박지 않는다** | 어두운 중립색(`chart.text`)을 쓴다 |
| 투명 배경 | — | **굽지 않는다.** 비우면 넣는 쪽 바탕에 따라 글자가 사라진다 |
| 채색 글자 | 두 바탕에서 다 읽히는 중간 명도 | 같다 (팔레트가 정한다) |

**색은 화면과 다른 값이다.** 화면은 지금 그대로 두고 png 만 가이드 팔레트에
맞췄다 — 조건이 다르므로 같은 값을 강요하지 않는다. 뜻은 유지한다: 계시 색은
**단가가 높을수록 짙고**, 줄어드는 쪽은 블루, 늘어나는 쪽은 코랄이다.

#### 슬라이드 차례와 레이아웃

**괄호 하나가 슬라이드 한 장이다.** 차례는 `slides.slide_specs()` 하나가 쥐고
덱은 그 목록대로 만들어진다 — 자리표와 실물이 갈라질 자리를 두지 않는다.
**수단을 하나도 켜지 않으면 수단별 장만 빠진다** (Word 와 같은 규약).

**잉여가 생기면 태양광 다음에 한 장이 붙는다** (53세션). 개선안으로 되돌리는
것이 아니다 — 수단 목록은 41세션 이후 여섯 그대로이고, 이 장은 **태양광의
결과 한 장**이다. `DocumentSections.surplus` 가 `None` 이면 만들어지지 않는다.

**자리는 실측해서 나눈다** (53세션 9절). 표 높이는 우리가 넘긴 값이 아니라
**줄 높이의 합**이고, 각주 높이는 줄 수에 따라 다르다 — `_note_top()` 이
각주 띠가 시작하는 y 를 재고 `_table_room_above()` 가 그 위까지만 표에 준다.
못박아 둔 값(`_NOTE_HEIGHT`)으로는 각주가 세 줄일 때 표가 그 위에 얹혔다.

**같은 형태를 반복하지 않는다.** `SlideSpec.layout` 이 형태이고 시험이 개수를
센다 — 수단별 장을 뺀 나머지에서 형태가 다섯 가지 이상이고 한 형태가 세 장을
넘지 않아야 한다.

| 형태 | 어디 |
|---|---|
| `cover` | 표지 — 전체 배경 밴드가 다크다 |
| `agenda` | 목차 — 리스트형, 구분선으로 나눈다 |
| `table` | 건물현황 · 개선안별 요약 · 부록 — **구분선 기반이고 카드가 아니다** |
| `chart` | 그림 한 장을 크게 — 지금 차례에는 쓰이지 않는다 |
| `stat_chart` | 전력사용현황 및 부하패턴 · 피크특성(1/2) · 그림 한 장짜리 수단 장 |
| `chart_pair` | 피크특성(2/2) · **그림 둘짜리 수단 장**(역률·태양광) |
| `stat_table_chart` | ESS — 지표 + 폭 전체 사양 표 + (자리가 남으면) 그림 (46·53세션) |
| `fact_stat_chart` | 계약전력 조정 — **근거 지표가 먼저**, 결과 지표가 뒤 (53세션) |
| `split` | 현재 요금 구조 · **잉여 활용** — 좌우가 서로 다른 것을 담는다 |
| `compare` | 조합구성 및 합산효과 — 좌우 2단에 중앙 얇은 구분선 |
| `closing` | 다음 단계 — 표지와 짝이 되는 다크 배경 밴드 (37세션) |

**수단 장의 형태는 그림 수가 정한다** (38세션). `MeasureEntry.slide_figures` 가
둘이면 `chart_pair`, 하나면 `stat_chart` 다 — 화면이 그림 둘로 답하는 물음을
슬라이드가 하나로 줄이면 남은 하나가 무엇의 근거인지 알 수 없어진다. 화면
그림과 PPT 그림의 짝은 `tests	est_slides.py` 의 `SCREEN_TO_DECK` 가 쥐고,
화면에 그림을 더하고 슬라이드를 잊으면 시험이 잡는다.

**해석 한 줄과 용어 풀이는 `report\narrative.py` 가 쥔다** (39세션). 문장을
짓는 규칙은 셋이다 — ① 진단이 이미 판정한 것은 그 판정을 옮기고 근거 숫자를
붙인다 ② 판정이 없으면 값의 크기로 고르되 갈림값은 `assumptions.json` 에서
읽는다 ③ 값과 무관하면 고정 문장. 용어 풀이는 **화면 툴팁과 같은 원본**이라
`ui\views\diagnose.py` 가 같은 모듈을 꺼내 쓴다.

**미산출은 값과 사유를 가른다** (39세션). 지표 칸에는 「미산출」 만 두고
사유는 각주가 받는다 — `slides.split_reason()` 이 그 자리다. 큰 글씨 자리에
사유가 들어가면 두 줄로 흐르고 넷을 나란히 놓았을 때 위계가 무너진다.

**결론과 무관한 주의사항은 싣지 않는다** (39세션). `MeasureEntry.actionable`
이 거짓이면 실행 주의사항 대신 `facts` — **왜 여지가 없는지 보이는 숫자**가
그 자리를 받는다.

**글 덩어리는 줄 수를 세어 자리를 잡는다** (`_wrapped_height`). 높이를 못박아
두면 두 줄로 흐른 결론이 아래 지표 라벨과 겹친다.

**마크다운은 적는 순간 벗긴다** (38세션 · 39세션에 Word 까지). 문구는 화면(Streamlit)·Word 로도 가서
낳는 자리에서 고칠 수 없으므로, `notices.plain_text()` 한 곳이 별표·밑줄·백틱을
벗긴다 — PPT 는 `_text()` 와 `_table()`, Word 는 `_para()`·`_heading()`·표 칸이
그것을 지나고, 시험이 그 자리들을 훑는다.

**Word 의 그림 비율을 그대로 쓰지 않는다.** 9:3.6 은 문서 한 단(6.3in)에 맞춘
것이라 16:9 슬라이드의 반 칸에 넣으면 위아래가 통째로 남는다. 슬라이드가 자기
칸에 맞는 `size` 를 부를 때 정해 넘긴다. 범례가 바깥에 붙는 그림은 그만큼 폭이
늘어나므로 미리 좁혀 잡는다(`HALF_FIGURE_WITH_LEGEND`).

**샌드위치는 표지와 마무리다** (37세션). 36세션은 표지만 다크로 두었는데
지시서 목차에 마무리 장이 없었기 때문이고, 그래서 구조가 반쪽이었다. 다크
배경은 둘 중 하나를 **이름으로 고른다** (`colors.cover_background` ·
`colors.closing_background`) — 코랄처럼 작은 포인트로만 쓰는 색을 고르면
`Palette._band()` 가 막는다. 다크 배경 위의 구분선은 `on_dark_rule` 이다.
밝은 `rule` 을 그대로 그으면 검은 바탕에서 선이 내용보다 먼저 보인다.

**마무리가 말하는 것은 「다음 단계」 하나다** (`slides.NEXT_STEPS`). 이 검토는
초기 판단용이고 채택한 안은 현장에서 확정된다 — 덱 어디에도 없던 문구라 옮겨
올 것이 없었고, 시험이 **앞 장에 같은 말이 생기는 것**을 막는다. Word 에는
마무리 장이 없어 이 문구도 없다.

**PPT 부록에는 산출 근거만 싣는다.** ESS 조달 사례·적용 기준 데이터·알려진
한계 셋은 슬라이드에서 읽히지 않는 분량이라 뺐고, **Word 부록 A·B·C 와 Excel
에는 그대로 있다.** 근거 줄이 한 장에 다 안 들어가면 몇 줄을 뺐는지 적는다 —
조용히 자르면 「이게 전부」로 읽힌다.

#### Word 는 화면에서 감췄다

**단추만 없앴고 코드와 시험은 그대로다** (36세션 1절). 산출물이 셋이면 받는
사람이 「어느 것을 봐야 하나」 를 먼저 골라야 하는데, Word 와 PPT 는 같은
재료(`DocumentSections`)로 같은 이야기를 하는 두 매체라 고를 근거가 없다.
되살리는 방법은 `ui\views\compare.py` 의 「36세션 1절 · Word」 주석에 있다.

**CLI 배치는 손대지 않았다.** 거기서는 Word 를 애초에 만들지 않았고(케이스별
Excel 과 요약 CSV 뿐이다), 여러 건을 나란히 놓는 자리라 건별 문서가 쓰이는
자리가 아니다.

## 5. 기준 데이터와 갱신 {#tech-rules}

### 5.1 데이터 목록과 출처 {#tech-rules-list}

법령 유래 수치가 코드 상수로 흩어져 있으면 사람이 볼 수도 고칠 수도 없다.
근거와 확인일을 붙여 파일로 옮겼다.

| 파일 | 항목 | 근거 |
|---|---|---|
| `rules_kr.json` | **27개** | 조문 (약관 제41·42·43·56·57·58·68조, 운영규칙 제12장) |
| `assumptions.json` | **25개** | `"판단값"` |

**섞지 않는다.** 섞으면 "이 숫자를 우리가 정한 것인가 법이 정한 것인가"를
되물을 수 없는데, 그 물음이 갱신 판단의 전부다. **스키마가 이를 강제한다** —
법령 유래 항목에 근거 조문이 비면 파일 읽기가 거부된다.

담긴 것: 역률 9개 · 요금적용전력 4개 · 계약종별 임계 3개 · DR 3개 ·
계절·시간대·요일 5개 · 판단값 25개(감도 s · PV 밀도 · DR 분위수 · ESS 효율 ·
만료 임계 · 진행률 가중치 등).

#### 모듈 상수로 붙잡지 않는다 {#tech-rules-lookup}

**이것이 이 절에서 가장 중요하다.** 값을 파일로 옮기고도

```python
LAGGING_STANDARD_PCT = 92.0  # ← import 시점에 고정된다
```

처럼 붙잡아 두면 **화면으로 파일을 고쳐도 그 프로세스에서는 옛 값으로
계산된다.** 코드에 기본값을 남기는 것과 같은 사고이고, 값이 그럴듯해서 결과를
다 쓰고 나서야 발견된다. 전부 함수 조회로 바꿨다.

```python
def lagging_standard_pct() -> float:
    return float(rule_value("power_factor.lagging_standard_pct"))
```

**데이터클래스 필드 기본값도 같다.** `field(default_factory=...)` 라야 생성
시점에 읽는다. 그냥 기본값으로 두면 import 시점에 고정된다.

### 5.2 갱신 절차 {#tech-rules-update}

무엇을 언제 갱신하는지, 어떻게 고치는지는 **매뉴얼 7장**에 있다. 여기서는
설계 근거만 적는다.

**편집 방식을 데이터 성격에 따라 나눴다.**

| 방식 | 대상 | 이유 |
|---|---|---|
| 엑셀 왕복 | 요금 단가, 시군구 좌표 | 항목이 많고 표 구조다 |
| **화면 편집** | 기준 데이터 | 항목이 적고 **근거가 함께 보여야** 한다 |

되읽기는 **항목 키를 대조해** 행이 빠지거나 키가 바뀌면 거부한다. 조용히
항목이 사라지면 코드에 기본값이 없으므로 다음 실행이 멈추고 원인을 찾기 어렵다.

`set_value`·`confirm` 은 **순서를 지킨다.**

```
① 검증 → 실패하면 저장하지 않고 어느 항목이 왜 틀렸는지 돌려준다
② 편집 직전 상태를 backup\ 에 남긴다 (최근 10개)
③ rules_history.jsonl 에 한 줄 남긴다
④ 캐시를 비운다
```

**④가 없으면 파일은 바뀌었는데 계산은 옛 값으로 돈다.** 화면 쪽 캐시는 두
겹으로 막는다 — 편집 훅이 `st.cache_data.clear()` 를 부르고, 모든 캐시 키에
기준 데이터 지문을 물린다. 훅만 두면 엑셀 왕복·손편집을 놓치고, 지문만 두면
지문을 빠뜨린 캐시가 조용히 샌다.

**코드를 고쳐도 같은 병이 난다** (34세션). `st.cache_data` 는 **감싼 함수의
소스만** 해시한다 — 그 함수가 부르는 다른 모듈이 바뀌어도 키가 그대로다.
앱이 떠 있는 채로 코드를 고치면 Streamlit 은 스크립트를 다시 읽지만 **캐시는
들고 있어**, 소스는 새 값인데 화면은 옛 값이 된다. 33세션이 여기 걸렸다 —
조합 근거 문구를 고쳤는데 화면이 그대로였다(그 문구가 캐시된 `ComparisonResult`
안에 담겨 돌아온다). 그래서 `cache.rules_stamp()` 가 **패키지 소스의 지문**
(`cache.code_stamp()`)을 함께 문다. 파일 하나만 바뀌어도 모든 캐시 키가
달라진다. 지문은 프로세스마다 한 번만 재고, 크기와 수정 시각만 본다.

**요금표는 엑셀 변환이고 수기 입력은 금지다.** 60개 값을 손으로 옮기면 오차가
섞인다 — 실제로 엑셀의 농사용(을) 단가가 원본과 다르다(66.6 vs 68.6원).
계절 열은 **헤더 이름**으로 매핑한다. 산업용 시트만 봄·가을이 여름보다 앞이라
위치로 읽으면 태양광 평가가 정반대가 된다. **검증 실패 시 파일을 쓰지 않는다.**

**자동 수집은 하지 않는다.** 한전 요금표는 API 가 없고 연 1~2회 개정이라 수동
갱신이 현실적이다. 자동화하면 원문이 바뀐 것을 알아채지 못한 채 파싱만
실패하고 **그 실패는 조용하다.** 대신 만료 경고에 원문 확인처를 함께 싣는다.

만료 임계는 요금 단가 12개월 / 약관·규칙 24개월 / 참고단가 24개월 / 기상은
전년도 미확보 시다. **임계값도 `assumptions.json` 에 있다** — 코드에 두면
"왜 12개월인가"를 물을 곳이 없다.

### 5.3 원복과 이력 {#tech-rules-restore}

```
data\defaults\   출고 기본값. 커밋. 읽기 전용
data\            현재 값
data\backup\     편집 직전 스냅샷 (최근 10개, .gitignore)
```

| 원복 | 규약 |
|---|---|
| ① 직전 상태 | **되돌리기 자체도 백업한다** — 되돌린 것을 되돌릴 수 있어야 한다 |
| ② 출고 상태 | **확인 전에는 실행하지 않고** 달라지는 항목만 돌려준다 (`confirmed=False`) |
| ③ 항목별 | 한 항목만. 나머지는 건드리지 않는다. 실무에서 가장 많이 쓰인다 |

**여기서 버그를 둘 잡았다.**

1. **직전 복원이 방금 만든 상태를 되돌렸다.** 안전 백업을 쓰면 그것이 목록 맨
   앞으로 올라오는데 복원 함수가 목록을 다시 읽어 그 안전 백업을 복원했다.
   되돌릴 대상을 **미리 잡아 두는** 것으로 고쳤다.
2. **같은 분에 두 번 백업하면 앞엣것을 덮어썼다.** 파일명이 분 단위라 편집
   백업과 안전 백업이 같은 이름이 되어 편집 **직전** 상태가 사라졌다.

둘 다 시험이 없었으면 실사용에서, 그것도 "되돌렸는데 안 돌아간다"는 형태로
드러났을 것이다.

**요금적용전력 3규칙이 케이스마다 갈렸다** (PV 1,000 kWp).

| 판정 | 근거 |
|---|---|
| C1 > C2 (저감 폭) | **95.4 vs 5.8 kW** — C2 는 PV 가 오후 피크를 깎으면 저녁 슬롯이 새 최대가 된다 |

#### ESS 는 54세션에 들어왔다

**여섯 케이스를 다 훑으면서 ESS 만 한 번도 돌지 않았다.** 요금·진단·태양광·
감도는 케이스마다 재계산했는데 수단 행에는 선택요금·계약전력·역률·DR 넷뿐이었다
— 그래서 「고를 수 있는 목표가 없는데 목표를 내고, 그 목표로 다시 계산한
절감액이 음수」 인 갈래가 **66/66 을 통과한 채 실물에만** 나왔다.

이제 케이스마다 **화면과 같은 경로**(개략 곡선 → 정밀화)를 돌리고 넷을 판정한다.

| 판정 | 무엇을 막나 |
|---|---|
| 성립하지 않으면 목표가 0 | 없는 목표를 내는 것 |
| 목표를 냈으면 절감액 > 0 | 음수 절감액을 「최단 회수기간」 으로 부르는 것 |
| 목표 달성이면 실제 요금적용전력이 목표 이하 | 표가 스스로 어긋나는 것 |
| 절감액이 0 이하인 점에는 회수기간이 없다 | 회수기간 없는 줄에 표식이 붙는 것 |

**판정이 66 → 90 이 됐다** (케이스당 넷). 소요는 28초 → 47초다.

> **이 넷만으로는 그 갈래를 못 잡는다.** 여섯 케이스는 기본 단가에서 그 자리에
> 닿지 않는다 — 단가를 낮춰야 개략 곡선의 마진이 통과하고 정밀화가 후보를
> 못 찾는 상태가 된다. 그 조합은 `tests	est_ess_cost.py` 가 지킨다.
> **케이스 스터디가 막는 것은 「ESS 를 아예 안 본다」 는 것 자체다.**

> **판정 잣대를 한 번 바로잡았다.** 처음에 "기본요금 절감액 ÷ 기본요금"으로
> 견줬는데, **기본요금 자체가 요금적용전력에 비례하므로** 피크가 낮은 케이스일수록
> 같은 kW 를 깎아도 비율이 커져 뜻이 뒤집힌다. PV 가 실제로 하는 일은 kW 를
> 깎는 것이므로 **요금적용전력 저감 폭(kW)**으로 바꿨다.

수기 케이스 7건이 요금 엔진을 따로 지킨다. **그중 하나에서 손계산이 틀렸다** —
토·일 11~14시를 모두 중간부하로 봤는데 **일요일은 전량 경부하**였다. 엔진이
맞았고 수기 케이스가 제 역할을 했다.

#### 최적화 이력 — Period 박싱 제거 {#tech-optimization}

물음은 "PV 발전량을 20단계 × 감도 3 = 60회 다시 계산하는가"였고 **답은
아니오**였다. 시뮬레이션은 1회, 용량은 곱셈이다.

되풀이되던 것은 **발전량이 아니라 요금**이었다. 프로파일러가 찍은 자리는
`calculate_bill` 시간의 **74%를 먹던 `PeriodArray._box_func` 180만 회**였다.

```python
for month in months:  # 13개월
    month_mask = slots["month"].to_numpy() == month  # 3만 5천 개를 매달 상자에
```

`slots["month"]` 는 Period 열이라 `to_numpy()` 가 그때마다 전 슬롯을 파이썬
`Period` 객체로 상자에 넣는다. 루프 밖으로 한 번만 끌어올렸다.

| | 전 | 후 |
|---|---|---|
| `calculate_bill` 1회 | 0.63초 | **0.145초** (4.3배) |
| 파이프라인 전체 | 24.6초 | **9.4초** (2.6배) |
| 케이스 스터디 6종 | 114.2초 | **29.9초** (3.8배) |
| pytest 전체 | 324초 | **98초** (3.3배) |

**회귀값은 한 자리도 바뀌지 않았고** 케이스 스터디 66/66 그대로다.

**교훈.** 시간만 봤으면 "곡선이 느리다"에서 멈췄다. 호출 수를 함께 세었기에
발전량이 아니라 요금이 곱해진다는 것을 먼저 알았고, 프로파일러가 그 안의
진짜 자리를 찍었다.

#### 메모리 측정 {#tech-memory}

Windows 작업 집합을 `GetProcessMemoryInfo` 로 직접 읽는다. `tracemalloc` 은
파이썬 할당자만 보므로 **NumPy 배열이 빠지는데**, 이 도구에서 메모리를 쥐는
것이 바로 그 배열이다.

> `ctypes` 호출에서 `argtypes` 를 지정하지 않아 64비트에서 핸들이 잘렸고,
> 호출이 **조용히 실패해 0 이 돌아왔다.** 표에 "0 MB"로 찍혀 있었다 — 못 잰
> 것을 안 썼다고 읽을 뻔했다. 지금은 못 재면 `None` 이고 표에 `—` 로 나온다.

### 7.2 미해결 항목 7건 {#tech-open-items}

**넷 다 "모르는 것을 모른다고 표시하는" 상태로 처리되어 있다.** 금액을 지어내지
않으므로 도구는 그대로 쓸 수 있고, 자료가 들어오면 값만 바꿔 끼우면 된다.

| # | 항목 | 무엇이 있어야 풀리나 |
|---|---|---|
| 1 | **요금 엔진 검증** | 한전 청구서 한 벌. `verified` 를 true 로 바꾼다. **일요일 경부하 계량을 가장 먼저 대조한다** (수기 케이스에서 월 6.2% 차이) |
| 2 | 요금적용전력 직전 이력 | 청구서. 없으면 첫 11개월이 과소 산출된다. `prior_peaks=` 로 주입 가능 |
| 3 | 실측 역률 | 청구서의 역률 항목. `power_factor_pct=` 로 넣으면 재계산 |
| 4 | 엑셀 요금표 옮김 오차 대조 | 청구서와 함께. 농사용(을)에서 오차를 발견했으므로 **같은 표에 더 있을 수 있다** |
| 5 | 태양광 참고단가 | 공개 자료(보급통계·공공조달 단가). 구조는 열어 두었다 |
| 7 | Open-Meteo 라벨 규약 | 실측 발전 곡선. 30분 밀렸는지 대조 ([4.7](#tech-weather)) |

**6번 자리는 비어 있다 — 90세션에 닫았고 채우지 않는다.** 「교육용(갑) 고압의
요금적용전력 하한 비율」 이었고, 시행세칙 별표4 원문을 읽어 **30%** 로 정했다.
**그 자리에 새 항목을 밀어 넣지 않는다** — 60·67·71세션이 번호를 물려 쓰다
서로 다른 항목을 같은 번호로 부르는 일을 세 번 겪었다. 90세션이 연 것은
자료를 기다리는 것이 아니라 **우리 손에 달린 것**이라 이 표에 오지 않는다
(`PROCEED.md` 「미해결 항목」 ②).

**6번은 세 세션에 걸쳐 닫혔고, 그 자리에 남은 조각이 다시 6번이 됐다.**
61세션에 약관 제38조 원문을 확보해 (`data\source\2024-10-24_기본공급약관_검색용.txt`)
제2항을 확인하고 **갑Ⅱ 둘을 옮겼고**, 87세션에 판정을 세우고, 88세션에 못을
박고, **89세션에 고쳤다.**

**89세션에 무엇을 했나.** `base_fee_basis` 를 전압구분 안에도 둘 수 있게 했다 —
종별 값이 기본값이고 `voltages\<전압>\base_fee_basis` 가 그것을 덮는다.
교육용(갑)의 기본값을 `billing_demand` 로 옮기고 **저압 하나만** `contract` 로
덮었다. 갑Ⅰ 둘은 **한 자도 안 고쳤다** — 아래 표의 첫 줄이 그 까닭이다.

| 종별·전압 | 88세션까지 | 89세션 | 왜 |
|---|---|---|---|
| 갑Ⅰ **고압** (일반용·산업용) | 계약전력 | **계약전력 — 그대로** | 제57조 ④·제59조 ⑤가 「갑 고압은 갑Ⅱ를 적용한다」 고 못을 박는다. 갑Ⅰ 고압 행이 쓰이는 자리는 **저압계량 예외 경로**뿐이다 |
| 갑Ⅰ·교육용(갑) **저압** | 계약전력 | **계약전력 — 그대로** | 제38조 ④+세칙 제24조 ②(20kW 이상 재량) · 제38조 ③(교육용 저압 재량). 기본값은 제68조 ② |
| 교육용(갑) **고압A·B** | 계약전력 | **요금적용전력 (제68조 ①)** | 제38조 ②로 계량기가 **선다.** 교육용에는 갑Ⅱ 가 없어 위 단서가 서지 않는다 |

**84세션의 「갑Ⅰ 고압A 실측 하나」 는 그 조건절 안에서 옳았다.**
병은 **한 사례를 세 종별에 편 것**이었다 — 조건절을 함께 옮기지 않았다.

**얼마나 틀렸나** — 균일 400 kW · 계약전력 5,800 kW 로 재면 교육용(갑) 고압A
선택Ⅰ 기본요금이 이렇게 움직였다. **89세션은 기준만 옮기고 하한을 안 걸었다.**

    88세션까지  5,800 kW × 5,550원 = 32,190,000원   계약전력 (제68조 ②)
    89세션        400 kW × 5,550원 =  2,220,000원   하한이 비어 있었다
    90세션      1,740 kW × 5,550원 =  9,657,000원   하한 30% 가 이긴다

관측 400 kW 가 하한 1,740 kW 에 못 미치므로 요금적용전력은 하한이고, 계약전력
기준과의 차이는 **하한 비율의 역수 3.33배**로 고정된다.

**하한 비율은 90세션에 정했다 — 교육용 둘 다 30% 다.**

시행세칙 별표4 원문을 읽었다. **제68조 ①의 30% 는 종별로 갈리지 않는다** —

설치한 고객」 전체를 대상으로 하고, 그 뒷문장이 「가장 큰 최대수요전력이
계약전력의 30% 미만인 경우에는 계약전력의 30%를 요금적용전력으로 합니다」 다.
곧 **기준이 요금적용전력이면 하한도 함께 온다.**

**교육용(을)의 15% 는 종별 특례가 아니었다.** 별표4 8.「초·중·고교 및 유치원
전기요금 적용」 은 이렇게 적혀 있다 — **91세션에 전문으로 다시 옮겼다.**
90세션은 기본요금 항만 떠 왔는데 **특례가 바꾸는 것은 그 항 하나가 아니다.**

**갑/을을 가르지 않는다.** 가르는 것은 **어떤 시설인가**와 **신청했는가**다 —
6세션이 이것을 종별 속성으로 읽어 교육용(을) **전체**에 15% 를 얹고 있었다.
**하한만 떼어 넣을 수 없다** — 특례 자체는 미해결로 열려 있다.

**특례가 바꾸는 것은 셋이다** (91세션 2절에 세었다).

| 무엇 | 지금 도구 | 특례 | 어디를 고쳐야 하나 |
|---|---|---|---|
| ① 요금적용전력의 창 | 직전 12개월 중 12·1·2·7·8·9월분과 당월분의 최대 | **당월분 하나** | `tariff\demand.py:billing_demands` |
| ② 하한 비율 | 계약전력의 30% | 계약전력의 **15%** | 요금표의 `contract_floor_ratio` |
| ③ 계절 할인 | **없다** | 12∼2월분·7∼8월분의 전력량요금 등에 기본사용 **6%** · 냉난방 **50%** | 엔진에 항목이 아예 없다 |

**값으로 셌다** — 소형 학교 벌(`small-edu-a`, 교육용(갑) 고압A 선택Ⅰ,
자료 2023-04-25 ~ 2024-04-27) 한 벌을 특례 적용 전후로 계산했다.

| 항목 | 계약 300 kW | 계약 950 kW (`small-edu-a-over`) |
|---|---|---|
| 기본요금 현행 | 17,404,897원 | 18,981,000원 |
| 기본요금 특례 | **15,644,812원** (−1,760,085원 · −10.1%) | **15,644,812원** (−3,336,188원 · −17.6%) |
| 전력량요금 할인 | **−5,256,153원** (전력량요금 102,776,884원의 5.1%) | 같다 |
| 합계 움직임 | **−7,016,238원** (−5.8%) | **−8,592,341원** (−7.1%) |

**셋 가운데 값이 가장 큰 것은 ③ 이다** — 기본요금 쪽(①+②)보다 세 배 가까이
크다. 「15% 특례」 라는 이름으로만 기억하면 **큰 쪽을 통째로 빠뜨린다.**

**그리고 결론이 뒤집히는 자리가 있다.** 계약 950 kW 벌은 지금 계약전력 조정
절감액이 **1,338,000원**인데(하한 285 kW > 최대수요 264.7 kW), 특례를 적용하면
하한이 142.5 kW 로 내려가 **최대수요에 져서 절감액이 0 이 된다.** 특례는
기본요금만 깎는 것이 아니라 **개선 수단 하나의 판정을 통째로 바꾼다.**

**센 값에 붙는 단서 셋.**

- **③ 할인은 과소 산출이다.** 조문은 「전력량요금, 기후환경요금 및 연료비조정
  요금을 합산한 금액」 에 걸리는데 이 도구는 **전력량요금만 계산한다** —
  뒤 둘이 빠진 만큼 실제 할인은 위 수보다 크다.
- **기본 사용전력량의 평균에 부분 월을 넣지 않았다.** 자료가 2023-04-25 에
  시작해 4월분이 6일치라, 7∼8월분의 기준이 되는 4∼6월분 평균을 **5·6월
  둘로만** 냈다.
- **냉난방 사용전력량이 음수가 되는 달은 0 으로 봤다.** 조문은 「차감하여
  산정한다」 뿐이고 음수 처리를 정하지 않았다. 이 자료에서는 12월분·2월분이
  그렇다.

**97세션에 실물과 다시 맞댔다 — 91세션 인용이 한 글자도 안 틀렸다.**
`data\source\2026-06-01_기본공급약관시행세칙(합본).pdf` **388쪽**(세칙 374면)이다.
「유치원」 이 나오는 쪽은 셋(138 · 326 · 388)이고, 별표4 구간(340~456쪽)에
**중복적용을 막는 총칙은 없다.**

**라.(적용제한)은 다른 할인과의 중복을 막는 조항이 아니다.** 한 전기사용계약에
초·중·고교와 대학 등이 섞여 있을 때 **대상시설을 별도 계약 단위로 분리한
경우에 한하여** 나.가 붙는다는 **계약 단위 요건**이다 — 곧 **대상을 좁힌다.**
도구는 계약 단위 구성을 모르므로 이 요건을 판정할 수 없다.

**마.(적용기간)은 「2017년 1월분 요금부터」 이고 끝이 없다.** 신청일 조항은
마.가 아니라 **나.(3)** 이다. 부칙 (2016.12.31 · 326쪽)에 2016년 12월분~2017년
2월분의 유리원칙 경과조치가 있었으나 **그 창은 지났다.**

**갑/을이 글자로 서지 않는다** — 가~마 전체에 「갑」·「을」·「고압」·「저압」 이
한 번도 안 나온다. 같은 세칙 제41조 ③(138쪽)이 교육용전력 대상을 여섯으로
열거하는데(**대학**·평생학습관·**도서관** 포함) 특례는 그 가운데 초·중등교육법
제2조와 유아교육법 제2조 제2호만 집는다. **가르는 축은 시설 하나다.**

**할인 대상이 전력량요금만이 아니다** — 조문은 「전력량요금, 기후환경요금 및
연료비조정요금을 **합산한 금액**」 이라고 적는다. 이 도구는 전력량요금만
계산하므로 **③ 할인은 구조적으로 과소 산출**이고, 그 사실이 산출물에 나간다.

**조문이 정하지 않은 것 여섯** (91세션이 하나를 적었고 97세션에 다섯을 더했다).

| # | 무엇 | 조문이 말하는 데까지 |
|---|---|---|
| 1 | 냉난방이 음수인 달 | 「차감하여 산정한다」 뿐 |
| 2 | 기준월이 없거나 부분 월일 때 | 「평균하여 적용한다」 뿐 |
| 3 | 「월분」 이 검침월인가 달력월인가 | 「월분」 이라고만 쓴다 |
| 4 | 비중 안분의 기준 | 「전력량 비중으로 구분」 — 시간대 단가가 다른 금액을 전력량 비중으로 나누는 것이 맞는지는 말하지 않는다 |
| 5 | 신청일 | 나.(3)이 신청일 기준인데 신청일을 알려주는 자리가 없다 |
| 6 | 라.의 계약 분리 여부 | 계약 단위 구성 정보가 조문 밖이다 |

#### 어디에 넣나 (97세션 3절)

**종별을 쪼개지 않는다. 시설 속성으로 따로 단다.** 종별을 넷으로 쪼개면
6세션의 오독(교육용(을) **전체**에 15%)을 구조로 박는다.

**사용자가 보는 것은 라벨 하나이고 안에서 값이 둘로 갈린다.** 계약 정보의
입력 칸은 **넷 그대로**이고 「계약종별」 선택지 수만 는다.

    교육용전력(갑) · 초·중·고·유치원   → education_a + 특례 참
    교육용전력(갑) · 그 밖             → education_a + 특례 거짓

**자격 종별을 코드에 박지 않는다.** `rules_kr.json` 의
`school_exception.contract_types` 에서 읽는다 — 근거는 별표4 8. 가.와 약관
제58조다. 요금표(단가)에는 시설 속성을 둘 자리가 없다.

**신청일은 `assumptions.json` 에 못 담는다** (94세션 판정을 97세션에 다시
확인했다). 49항목이 **전부 코드가 읽는 값**이고(둘은 `tools\screen_budget.py`
가 읽는다) 「값 없는 판단」 을 담는 자리가 없다. 그래서 **분석 기간 전체에
적용하고 그 사실을 화면이 말한다.**

| 종별 | 89세션까지 | 90세션 | 근거 |
|---|---|---|---|
| 교육용(갑) | `null` (미적용) | **0.3** | 제68조 ① |
| 교육용(을) | 0.15 | **0.3** | 제68조 ① (15% 는 별표4 8. 의 신청 특례) |
| 나머지 여섯 | 0.3 또는 `null` | **그대로** | 갑Ⅰ 둘만 `null` — 전 전압이 계약전력 기준이다 |

**하한을 거는 자리도 함께 옮겼다.** 종별 값이 아니라 **그 전압의 기본요금
기준**이 정한다 — 계약전력 기준(제68조 ②) 전압에서는 값이 있어도 걸지 않고
결과에도 싣지 않는다. 그러지 않으면 교육용(갑) **저압**이 없는 하한으로
계약전력 조정 목표를 세운다.

### 7.3 확장 방향 {#tech-extension}

| 방향 | 메모 |
|---|---|
| 종별 확대 | 요금표 JSON 에 종별을 더하면 된다. 검증 규칙이 먼저 깨지지 않도록 [부록 A](#부록-a-요금-데이터-스키마) 참조 |
| 편차 보정 | 분위수 사상으로 예측 분포를 실측에 맞춘다. **실측 발전 데이터가 쌓인 뒤** |
| 신뢰성DR | 설비 요건 판정이 필요하다. 현재 범위 밖 |
| 다중 사업장 | CLI 배치가 이미 순차 처리한다. 화면은 한 건 기준 |
| 화면 캡처 | 매뉴얼에 자리만 잡아 두었다. `CAPTURES.md` 참조 |

**메모리 여유가 생겼다고 다중 시나리오를 동시 적재하지 않는다.** 순차 처리를
유지한다 — 케이스 6종의 시계열을 동시에 들지 않는 것이 그 규약이다.

|---|---|---|
| 1 | 시간대 단가 `경 < 중간 < 최대` | `time_of_use=true` 종별만 |
| 2 | 선택요금 간 균일성 | 선택Ⅲ 미적용 (할인이 최대부하에 집중된 설계다) |
| 3 | 기본요금 단가 양수 | 전부 |
| 4 | 계절 3종이 모두 있을 것 | 전부 |

**전체시간 종별**(갑Ⅰ·교육용(갑))은 세 시간대에 같은 단가 + `time_of_use=false` 다.
스키마를 갈라 두면 엔진이 두 갈래가 되므로 **검증만 갈랐다.**

**검증 정책은 코드에 둔다** (`validate.DEFAULT_POLICY`). 요금 단가가 아니라
데이터에 대한 우리의 기대이고, 요금표를 갱신했다고 검증기가 먼저 깨져서는
안 된다.

**단가를 임의로 고치지 않는다.** 검증 실패는 경고로 남기고 규칙 쪽을 검토한다.
고치면 요금표 조작이 된다.
