# kWise 기술서

건물 전력 비용 진단·개선안 비교 도구. **개발자와 1년 뒤의 본인**이 읽는다.

이 문서는 **왜 그렇게 만들었는가**를 남긴다. 무엇을 하는지는 코드가 말하고,
어떻게 쓰는지는 매뉴얼이 말한다. 코드가 바뀔 때 갱신한다.

| | |
|---|---|
| 사용법 | `MANUAL.html` — 화면 조작과 결과 읽는 법 |
| 요구사항 | `REQUIREMENTS_kwise.md` — 무엇을 만들기로 했는가 |
| 진행 이력 | `PROCEED.md` — 세션별 기록과 결정 사항 |
| 근거 조문 | 이 문서 [부록 C](#부록-c-근거-조문-색인) — **한 곳에 모았다** |

## 1. 개요와 시스템 환경 {#tech-overview}

### 1.1 개발 배경과 목적 {#tech-purpose}

한전 15분 실측 사용량으로 **전력 비용 구조를 진단하고 개선 수단을 견준다.**

처음 이름은 `peakcut` 이었고 태양광 피크 저감이 주인공이었다. 샘플 데이터를
돌려 보고 방향을 바꿨다 — **설비 투자 없이 선택요금 전환만으로 연 5,358만원**이
나왔다. 태양광부터 묻는 구조는 이 값을 가린다.

| | 이전 | 현재 |
|---|---|---|
| 목적 | 태양광 도입 시 절감액 산출 | 비용 구조 진단 + 개선 수단 비교 |
| 태양광 | 주인공 | 개선 수단 중 하나 (7.5) |
| 첫 산출물 | PV 피크 저감량 | **투자 없이 가능한 절감액** |
| 화면 | 업로드 → PV 입력 → 결과 | 1 진단 → 2 수단 → 3 비교 |

**설계를 관통하는 원칙 셋.**

1. **모르는 것은 모른다고 표시한다.** 금액을 지어내지 않는다. 단가를 넣지
   않으면 투자비는 0원이 아니라 `None` 이고 사유가 붙는다.
2. **코드에 기본값을 두지 않는다.** 법령 유래 수치와 판단값은 파일에 있다.
   코드에 남기면 파일을 고쳐도 반영되지 않고, 값이 그럴듯해서 결과를 다 쓰고
   나서야 발견된다.
3. **조용히 빼지 않는다.** 검토하지 않은 수단은 "효과 없음"이 아니라
   "미검토"로 적는다.

### 1.4 용어와 약어 {#tech-glossary}

**이 절이 나머지를 짧게 만든다.** 도메인 용어를 여기서 한 번만 정의한다.

| 용어 | 뜻 |
|---|---|
| **요금적용전력** | 기본요금을 매기는 kW. 관측 최대수요가 아니다. 세 규칙이 걸린다 ([4.2](#tech-billing-demand)) |
| **최대수요전력** | 15분 평균 전력의 최대. 순시 전력이 아니다 |
| **계약전력** | 청구서에 적힌 계약 용량. 갑 종별은 이것이 기본요금 기준이다 |
| **경부하 / 중간부하 / 최대부하** | 시간대 구분. 경부하는 보통 22~08시. **요금적용전력은 경부하를 뺀다** |
| **대상월** | 요금적용전력 이월 대상. 7·8·9 · 12·1·2월. **전력량요금의 계절과 다르다** |
| **선택요금 (Ⅰ·Ⅱ·Ⅲ)** | 같은 종별 안의 요금제. 기본요금과 전력량요금 단가를 맞바꾼다 |
| **갑 / 을** | 계약전력 임계로 갈린다 (일반·산업 300 kW, 교육 1,000 kW) |
| **역률 (지상/진상)** | 유효전력 ÷ 피상전력. 지상은 유도성, 진상은 용량성 |
| **부하율** | 평균 부하 ÷ 최대 부하 |
| **기저부하** | 야간 평균 부하. 상시 가동 설비의 크기 |
| **CBL** | Customer Baseline Load. DR 정산의 기준 부하. **전력거래소가 산정한다** |
| **경제성DR** | 하루 전 자발적 입찰 수요반응. 신뢰성DR(의무 감축)은 범위 밖 |
| **kWp** | 태양광 모듈 **직류** 정격. 인버터 교류 출력과 다르다 |
| **GCR** | Ground Coverage Ratio. 모듈 면적 ÷ 부지 면적. 이격 거리의 척도 |
| **자가소비 / 잉여** | 발전량 중 그 시각 부하가 먹은 몫 / 남은 몫 |
| **첨예도 (sharpness)** | 발전 곡선의 뾰족한 정도. 감도 축이다 ([4.5](#tech-sensitivity)) |
| **요금 재계산** | 수단을 적용한 부하로 요금을 처음부터 다시 구하는 것. 절감액을 더하지 않는다 |
| **확실성 등급** | 높음 / 중간 / 중간~낮음. 산출 근거의 단단함 |

## 2. 시스템 구조 {#tech-architecture}

### 2.1 아키텍처 {#tech-layers}

**한 방향으로만 흐른다.** 아래 계층이 위를 부르지 않는다.

```
io ──→ quality ──→ tariff ──→ diagnose ──→ measures ──→ compare ──→ report ──→ ui
                      ↑           ↑            ↑            ↑           ↑
                    rules       pv          rules      progress     frames
```

| 패키지 | 책임 | 부르지 않는 것 |
|---|---|---|
| `io` | 파일 → `UsageData` (15분 kW·kWh·메타) | 요금·설비 |
| `quality` | 결측·정전·편중·이상치 | 요금 |
| `tariff` | 요금 계산. **순수 함수** | 설비·화면 |
| `pv` | 기상 취득·시뮬레이션·정렬·첨예도 | 요금 |
| `diagnose` | 6장 진단. **설비 정보를 받지 않는다** | 개선 수단 |
| `measures` | 7장 수단 7종 | 화면 |
| `compare` | 8장 조합 재계산 | 화면 |
| `report` | Excel·Word·차트 프레임·배치 | 화면 |
| `rules` | 기준 데이터 (전 계층이 함수로 조회) | — |
| `progress` | 진행 보고 프로토콜 | **streamlit** |
| `ui` | Streamlit 화면. **계산을 담지 않는다** | — |

**`ui` 를 뺀 어느 모듈도 `streamlit` 을 import 하지 않는다.** 시험이 이를
강제한다 (`test_progress.py`). 화면은 콜백만 넘긴다 ([4.1](#tech-flow)).

`ui` 안에서도 갈라 둔다.

| 순수 (시험이 닿는다) | Streamlit |
|---|---|
| `anchors` `text` `spec` `charts` `labels` `rules_view` `pipeline` `session` | `app` `nav` `callout` `state` `cache` `memo` `progress` `views\` |

판단이 들어가는 것(화면 순서·정렬·표기·조합 구성)은 전부 순수 쪽에 있다.

**차트는 프레임과 사양을 가른다** (15세션에 여섯을 더했다).

    report.frames    표를 만든다 — 순수. 화면과 보고서가 **같은 표**를 본다
    ui.charts        altair 사양
    report.figures   matplotlib png

각자 표를 만들면 같은 이름의 차트가 서로 다른 수를 그리게 되고, 그 어긋남은
눈으로 잡히지 않는다.

**표시 이름은 요금 계층에 있다** (`tariff.labels`). 계산 모듈이 내는 문구에도
종별 이름이 들어가는데(선택요금 전환 노트), 화면 쪽에만 두면 계산 모듈이 쓸 수
없어 `general_b/high_a/II` 가 그대로 화면에 나간다 — 15세션 통합 시험이 잡았다.

### 2.2 디렉터리와 설정 파일 {#tech-layout}

```
src/kwise/          패키지 (pip install -e .)
tools/              CLI 스크립트. 변환 로직은 src 에 두고 여기는 진입점만
tests/              pytest. 파일 하나가 계층 하나에 대응한다
data/               기준 데이터·요금표·기상 (2.3)
input/              샘플·합성 케이스 부하. 검증 재현용으로 커밋한다
docs/               요구사항서·기술서·매뉴얼
output/             산출물. casestudy_*.xlsx 만 커밋한다
cache/              중간 산출물. PROJECT_CACHE 로 옮길 수 있다
reference/          기존 pv_peak_cut 코드. **읽기 전용**
```

`pyproject.toml` 한 곳에 빌드·ruff·mypy·pytest 설정을 모았다. 설정 파일을
흩어 놓지 않는다.

### 2.3 데이터 구성 — DB 를 쓰지 않는다 {#tech-data}

**DB 를 두지 않은 이유.** 쓰기가 없다. 사용자가 올린 부하는 그 세션에서만
살고, 기준 데이터는 사람이 드물게 고치는 47여 항목이며, 기상은 읽기 전용
아카이브다. DB 를 넣으면 스키마 이관·백업·연결 관리가 생기는데 그 대가로
얻는 것이 없다. **파일이 곧 형상 관리 대상**이라는 점이 오히려 이득이다 —
`git diff` 로 요금 단가 변화를 볼 수 있다.

| 파일 | 형식 | 내용 | 갱신 |
|---|---|---|---|
| `data/tariff_kr_*.json` | JSON | 요금표 8종별 × 전압 × 선택요금 ([부록 A](#부록-a-요금-데이터-스키마)) | 엑셀 원본에서 변환 |
| `data/rules_kr.json` | JSON | **법령 유래** 27항목. 근거 조문 필수 | 화면·엑셀 |
| `data/assumptions.json` | JSON | **판단값** 25항목 | 화면·엑셀 |
| `data/defaults/*.json` | JSON | 출고값. 읽기 전용, 커밋 | 손대지 않는다 |
| `data/backup/*.json` | JSON | 편집 직전 스냅샷 최근 10개 | 자동 |
| `data/rules_history.jsonl` | JSONL | 편집 이력 한 줄씩 | 자동 |
| `data/sigungu_kr.json` | JSON | 시군구 229개 좌표 | 드물게 |
| `data/ess_cost_cases.json` | JSON | ESS 조달 사례 (회귀 원자료) | 24개월 |
| `data/ess_cost_model.json` | JSON | ESS 투자비 모델 (재적합 산출물) | 24개월 |
| `data/ess_cost_reference.json` | JSON | LCOS 참고단가 (차익거래·전망 전용) | 24개월 |
| `data/weather/*.parquet` | parquet | 기상 135격자 × 3개년, 405파일 40 MB | `fetch_weather.py` |

**기상만 parquet 인 이유.** 격자 하나·한 해가 8,760행 × 5열이다. JSON 이면
읽기가 느리고 용량이 몇 배가 된다. `int16` + 스케일 팩터로 양자화해
일사 0.1 W/m², 기온·풍속 0.01 단위로 담는다 — 계산에 충분하고 40 MB 에 들어간다.
적설은 pvlib 경로에서 쓰지 않으므로 **저장하지 않는다.**

## 3. 환경 구축과 실행 {#tech-setup}

### 3.1 설치 {#tech-install}

```
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"
```

**가상환경은 프로젝트 안의 `.venv` 다.** 셸이 활성화하지 않은 채 실행될 수
있으므로 `.venv\Scripts\python.exe` 를 직접 부른다.

Windows 전용 사항은 `ENVIRONMENT.md` 에 있다. 요약하면 셋이다 —
파일을 열 때 `encoding=` 을 반드시 명시할 것(기본이 cp949 다), 경로는
`pathlib.Path` 만 쓸 것, Excel 저장 전 tz-aware 컬럼을 해제할 것.

### 3.2 환경변수 {#tech-env}

| 변수 | 기본값 | 뜻 |
|---|---|---|
| `PROJECT_CACHE` | `.\cache` | 기상 캐시·세션 임시 폴더 |
| `KWISE_WEATHER_DIR` | `.\data\weather` | 사전 취득분 위치. 배포 시 옮길 수 있다 |
| `KWISE_TARIFF_DIR` | `.\data` | 요금표 위치 |

### 3.3 실행 {#tech-run}

화면과 CLI 사용법은 **매뉴얼 2장**에 있다. 여기서는 진입점만 적는다.

| 진입점 | 명령 |
|---|---|
| 화면 | `.venv\Scripts\streamlit.exe run src\kwise\ui\app.py` |
| 배치 | `.venv\Scripts\python.exe -m kwise.cli run --cases cases.yaml` |
| 케이스 스터디 | `.venv\Scripts\python.exe tools\run_casestudy.py --progress` |
| 성능 실측 | `.venv\Scripts\python.exe tools\run_benchmark.py` |
| 요금표 변환 | `.venv\Scripts\python.exe tools\build_tariff.py` |

## 4. 핵심 로직과 계산식 {#tech-core}

**이 장이 본체다.** 결론만 적지 않고 왜 그렇게 되었는지를 남긴다.

### 4.1 처리 흐름 {#tech-flow}

```
파일 ─→ load_usage()          15분 kW·kWh·메타. 24:00 → 다음날 00:00
      ─→ check_quality()      결측·정전·편중. 보간하지 않는다
      ─→ diagnose()           부하·피크·요금 구조·계약 적정성
      ─→ load_weather()       캐시 → API → 사전 취득분 → 중단
      ─→ unit_generation_kw() 1 kWp 프로파일. **한 번만** 시뮬레이션한다
      ─→ 수단 7종             각각 요금을 다시 계산한다
      ─→ compare_combinations()  조합마다 부하를 다시 만들어 재계산
      ─→ Excel / Word
```

여덟 단계에 진행 보고가 걸린다. **계산 함수는 `progress` 를 선택 인자로 받고
`step()` 만 낸다.** 단계 경계는 부르는 쪽이 긋는다 — 한 함수가 여러 단계에
쓰일 수 있기 때문이다. 화면은 Streamlit 어댑터를, CLI 는 rich 를 붙이며
**계산 쪽은 어느 쪽인지 모른다.**

진행률 가중치는 실측값이다 ([6.4](#tech-performance)). 균등 분할하면 태양광
구간(실제 52%)에서 막대가 몇 초 멈춘 것처럼 보인다.

#### 시각 규약 — 두 가지를 구분한다 {#tech-label}

**검침 라벨은 구간 끝이다.** 하루가 `00:15` 로 시작해 `24:00` 으로 끝나 96행이
된다. 구간 시작 라벨이면 `24:00` 이 나올 수 없다.

| 쓰임 | 기준 | 이유 |
|---|---|---|
| 계절·시간대·월 **귀속** | 라벨 − 1구간 (`slot_start`) | `15:00` 슬롯은 14:45~15:00 사용량이라 중간부하다 |
| 피크 발생 **시각 보고** | 라벨 그대로 | 청구서가 그렇게 적는다 |

첫 최대부하 슬롯은 `15:15` 이다. **PV 시계열을 붙일 때 같은 규약을 써야
15분 어긋나지 않는다** — 부하 라벨 L 에 붙일 발전량은 구간 중앙 `L − Δ/2` 의
순시 출력이다. 부하는 구간 평균이고 시뮬레이션은 순시값이라, 반 칸을
빠뜨리면 7.5분, 라벨을 그대로 쓰면 15분 밀린다.

### 4.2 요금 계산 {#tech-billing}

`calculate_bill()` 이 전부다. 순수 함수이며 **기본요금과 전력량요금만**
계산한다. 기후환경요금·연료비조정액·부가가치세·전력기금은 넣지 않는다 —
모두 사용전력량에 비례하므로 **실제 절감액은 산출값보다 크다.**

#### 요금적용전력 3규칙 {#tech-billing-demand}

기본요금의 기준이 되는 kW 다. 세 조건이 겹치므로 하나라도 빠뜨리면 크게
어긋난다 (약관 제68조).

| # | 규칙 | 내용 |
|---|---|---|
| ① | **대상 시간대** | 중간·최대부하만. 경부하(22~08시)는 제외. 공휴일은 전량 경부하로 계량되므로 자동 제외 |
| ② | **대상월 한정** | max(7·8·9월, 12·1·2월, 검침 당월) — 직전 12개월 안에서. 3~6·10~11월 피크는 **이월되지 않는다** |
| ③ | **계약전력 하한** | 계약전력 × 30% (교육용(을) 15% 특례). 종별 속성이며 `null` 이면 미적용 |

**①과 ②는 태양광에 반대 방향으로 작용한다.** ①은 PV 가 손댈 수 없는 야간·
공휴일 피크를 요금적용전력에서 빼 주므로 PV 에 유리하고, ②는 봄·가을 피크
저감의 가치를 없애므로 불리하다. **어느 쪽이 지배하는지는 부하 형태에 달렸다.**
케이스 스터디가 두 방향을 모두 확인했다 ([6.2](#tech-casestudy)).

`is_demand_month()` 를 `season_of()` 와 **따로 둔다.** 9월은 전력량요금상
봄·가을철이지만 대상월이고, 6·11월은 반대다. 같은 함수로 판정하면 두 규칙이
조용히 섞인다.

#### 계절·시간대·요일 {#tech-tou}

**손으로 옮겨 적지 않는다.** 값은 요금표 파일에 이미 있으므로 기준 데이터
생성 시점에 읽어 넣고, 두 벌이 어긋나지 않는지 시험이 지킨다.

> 옮겨 적기를 실제로 틀렸다. 여름 중간부하를 `[[8,11],[12,13],[18,22]]` 로
> 적었는데 실제는 `[[8,15],[21,22]]` 였다. 그 자리에서 규칙이 생겼다.

| 요일 | 계량 |
|---|---|
| 평일 | 그대로 |
| 토요일 | 최대부하 → **중간부하**. 경부하가 되는 것이 아니다 |
| 일요일·공휴일 | 전량 **경부하** |

**일요일도 공휴일로 계량한다.** `holidays` 라이브러리가 일요일을 담지 않는데
관공서 공휴일 규정에는 포함된다. 빠뜨리면 연 52일이 최대부하로 잘못 계량된다.

#### 기본요금 기준 — 갑과 을이 다르다 {#tech-base-fee}

| 종별 | 기준 |
|---|---|
| 을 | **요금적용전력** |
| 갑 | **계약전력**. 계약전력을 모르면 금액을 만들지 않고 멈춘다 |

섞으면 기본요금이 통째로 틀린다.

> **갑 종별 기준은 잠정이다.** 제68조 ②의 기준은 갑/을 구분이 아니라
> **최대수요전력계 설치 여부**다. 현재 구현은 관행적 대응이며, 특히
> 일반용(갑)Ⅱ 는 시간대별 구분계량기 고객이라 최대수요계를 함께 갖추었을 수
> 있다. 제38조 원문을 확인하지 못했으므로 **갑 종별 계산에 경고를 실어
> 화면·산출물로 내보낸다.** PoC 범위(일반용(을))가 이 경로를 타지 않아
> 샘플에서는 아무 일도 일어나지 않는다 — 그래서 갑 종별을 실제로 쓰는 첫
> 사람이 조용히 틀린 금액을 받게 된다.

#### 역률요금 {#tech-power-factor}

기본요금에 대한 **추가·감액**이다. 경고로 둘 수 없다 — 기본요금의 −1.0% ~
+6.4% 이고 샘플에서 1%가 453만원이다.

```
주간 08~22시  지상 기준 92%. 미달 시 1%p당 +0.2% (60%까지)
                            초과 시 1%p당 −0.2% (97%까지)
야간 22~08시  진상 기준 95%. 미달 시 1%p당 +0.2%
              단, 지상이면 100%로 간주 → 추가 0
```

**야간 진상 페널티는 '역률 개선 설비 과투자의 결과'다.** 제43조 ② 2호 나목이 지상이면
100%로 간주하므로, 대부분의 건물은 야간 경부하에서 지상이라 추가가 0 이다.
진상은 고정형 역률 개선 설비가 부하 대비 과다할 때만 생긴다. 그래서 이 조항은 "야간에도
역률을 관리하라"가 아니라 **"주간 역률을 맞추려 역률 개선 설비를 키우면 야간에 되돌려
받는다"**로 읽어야 한다.

**92% 가 두 조문에서 온다. 항목을 갈라 두었다.**

| 항목 | 조문 | 뜻 |
|---|---|---|
| `power_factor.lagging_standard_pct` | 제41조·제43조 ② | 역률요금의 **기준** |
| `power_factor.deemed_lagging_pct` | **제42조** | 무효전력계 미설치 시 **간주값** |

오늘은 둘 다 92% 라 묶고 싶어진다. 묶으면 **기준만 90 으로 개정됐을 때
역률을 모르는 고객의 값까지 따라 내려가** 조정액이 0 이 아니게 된다 —
실측하지 않은 값으로 금액이 생기는 것이다.

우리 데이터는 15분 유효전력뿐이라 제42조의 30분 누적 계량을 재현할 수 없다.
기본값 92%는 지어낸 값이 아니라 **그 조항이 무효전력계 미설치 고객에게
적용하는 간주값**이고, 그 값에서 조정액이 정확히 0 이다.

제43조 ③(첫 달 예고)은 **계산에 넣지 않는다.** 첫 달을 빼면 기간에 따라
금액이 달라져 도입 전후 비교(Δ)가 흔들린다.

#### 결측 월과 부분 월 {#tech-partial}

**결측을 보간하지 않는다.** 결측률이 문턱(5%)을 넘는 달은 관측 기준과 결측
보정 기준을 **함께** 낸다. 어느 쪽도 정답이라고 말하지 않는다.

부분 월은 기본요금을 **13개월분 부과하지 않기 위해** 계수를 곱한다. 기본
정책은 `merge` — 앞뒤 두 부분 월을 합쳐 한 달로 본다. 샘플에서 정확히
12.00개월분이 된다. 짝이 없으면 일수 비례로 물러서고 그 사실을 `notes` 에 적는다.

기간이 12개월 미만이면 **'연간'이라 부르지 않는다.** 실제 기간이나 12개월
환산으로 표기하고 환산 시 경고를 붙인다.

### 4.3 개선 수단별 산식 {#tech-measures}

**절감액은 언제나 재계산이다.** 수단을 적용한 15분 부하를 만들어
`calculate_bill()` 을 다시 부른다. 비율로 어림하지 않는다.

| # | 수단 | 산식 요지 | 확실성 |
|---|---|---|---|
| 7.1 | 선택요금 전환 | 같은 종별·전압의 모든 선택요금으로 요금을 다시 계산해 최소를 고른다 | 높음 |
| 7.2 | 계약전력 조정 | 요금적용전력 × (1+여유율) 로 권장값을 잡고 **하한 규정이 걸릴 때만** 금액이 난다 | 높음 |
| 7.3 | 경제성DR | 거래 가능일 × 등록 용량 × 입찰 시간 = 감축 가능량(kWh) | 중간 |
| 7.4 | 역률 개선 | 두 역률에서 각각 요금을 계산해 차를 낸다 | 높음 |
| 7.5 | 태양광 | 용량 곡선 20단계. 각 점에서 순부하를 만들어 재계산 | 중간 |
| 7.6 | ESS | 목표 요금적용전력에서 출력·용량을 역산하고 디스패치 후 재계산 | 중간~낮음 |
| 7.7 | 잉여 활용 | 상계는 그 슬롯 단가로, 판매는 단가가 있어야 산출 | 중간~낮음 |

**순서는 투자비 순으로 확정했고 바꾸지 않는다.** 수단을 더할 때마다 번호가
밀리면 코드 docstring 과 문서 참조가 계속 어긋난다. 목록은
`kwise.measures.MEASURE_CATALOG` 한 곳에 있고 화면과 보고서가 함께 읽는다.

#### 7.1 선택요금 전환 {#tech-tariff-switch}

**같은 계약종별 안에서만 견준다.** 종별은 용도로 정해지는 계약이지 고를 수
있는 요금제가 아니다. **전압구분도 현행에 가둔다** — 고압A(3.3~66 kV)와
고압B(154 kV)는 수전설비가 물리적으로 다르다. 단가만 보면 그럴듯한 권고가
나와서 더 위험하다.

드롭다운 생성(`list_selections`)은 가두지 않고 **전환 비교**(`switchable_selections`)만
가둔다. 둘은 쓰임이 다르다.

#### 7.2 계약전력 조정 {#tech-contract}

**하한 규정을 모르면 금액을 산출하지 않는다.** 일반용(을) 기본요금은
요금적용전력 기반이므로, 계약전력을 낮춰도 요금적용전력이 그대로면 요금이
그대로다. 줄어드는 경우는 하한(계약전력의 30%)에 걸려 있을 때뿐이다.
모르는 채로 금액을 내면 **없는 절감을 만들어내는 것**이 된다.

여유율 기본값은 판단값이다 (`contract.margin_ratio` = 0.1).

#### 7.3 경제성DR {#tech-dr}

근거는 전력시장운영규칙 제12장이다. **신뢰성DR 은 범위 밖이다.**

**거래일 제약이 이 절의 핵심이다** (제12.4.2.1조 1항 1호) — 공휴일과 **토요일**을
제외한 평일만 입찰할 수 있다. 빼면 감축 가능량이 30% 이상 과대평가된다
(샘플 359일 중 245일).

> **요금 계량의 '평일'과 다르다.** 요금 엔진은 토요일을 최대부하 → 중간부하로
> 낮출 뿐 공휴일로 보지 않는다. DR 은 토·일·공휴일이 모두 제외다. 그래서
> `dr_day_mask()` 를 따로 둔다. 같은 함수로 판정하면 두 규칙이 조용히 섞인다.

**연간 참여 일수 제한은 없다** (14세션에 바로잡았다). 13세션에 넣었던 「연 60시간
한도」는 전력거래소 확인 결과 경제성DR 의 제약이 아니었다. 남는 제약은 셋이다.

| 제약 | 값 |
|---|---|
| 하루 한도 | 최대 2회 × 1회 1~4시간 = **하루 8시간** |
| 참여 요일·시간 | 평일만 (토·일·공휴일 제외), 09:00~12:00 · 13:00~20:00 |
| 미이행 제재 | **6개월 입찰 제한** |

**따라서 실질 제약은 「감축할 여력이 있는 날이 며칠이냐」 하나다.** 데이터에서
찾는다.

    ① 기준선     주말·공휴일의 판정 시간대 평균 부하 (시장 시간대 ∩ 건물 운영 시간대)
    ② 저부하 평일 대상일 중 그 시간대 평균이 기준선 × 1.2 이하인 날 (배수는
                 assumptions.json 의 `dr.low_load_multiple`)
    ③ 감축 여력   평일 정상 평균 − 그날 실제 부하
    ④ 참여 시간   하루 8시간 상한, 저부하가 실제로 지속되는 시간까지
    ⑤ 감축 가능량 Σ(저부하일별 감축 여력 × 그날 참여 가능 시간)

샘플에서 저부하 평일은 **이틀**(2023-05-01·2023-10-02)이고 감축 가능량은
31,133 kWh/년이다. 걸린 두 날 모두 사무실을 비운 날이라, 하위 분위수 방식이
「항상 그만큼」 을 뽑던 것과 달리 **없으면 없다고 낸다.**

**보수적으로 산정한다.** 미이행이 6개월 입찰 제한이라 과대 산정의 대가가 크다.
등록 권장값은 **저부하일 감축 여력 분포의 하위값**이다 — 평균으로 등록하면
절반의 날에 미달하고 미달은 제재다 (별표26).

**저부하 평일 목록을 화면에 낸다.** 창립기념일·워크숍처럼 사무실을 비우는 날일
가능성이 높아, 그 날이 맞는지는 사용자가 판정한다.

**정산 단가에 기본값을 두지 않는다.** 전력거래소 월별 순편익가격 + 사업자
수수료라 우리가 만들 수 없다. 없으면 감축량(kWh)만 낸다.

**기본요금 절감을 계산하지 않는다.** SMP 기준 산발 입찰이라 참여일이 연중
최대수요일과 겹칠 확률이 낮다. 편익은 정산금 하나다.

0.1 MW-h 문턱(제12.4.2.1조 1항 2호)은 **수요관리사업자가 묶은 자원 단위**
기준이라 개별 고객 판정이 아니다. 참고 표시만 한다.

#### 7.5 태양광 {#tech-solar}

**기본 입력은 넷이다** — 설치 가능 면적·설치 밀도·지역·방위 (15세션에 방위를
더했다).

발전량 예측 R² 가 0.8 이라 **입력 정밀도가 기상 오차를 이길 수 없다.** 게다가
용량 곡선이 20단계를 훑으므로 면적 환산이 ±20% 틀려도 곡선 위 다른 점을 볼
뿐이다. 상세 입력은 확장 패널로 접는다. **모드를 나누지 않는다** — 상세 설계
모드를 만들면 pvsim 과 경계가 흐려진다.

```
설치 용량(kWp) ≈ 설치 가능 면적 × GCR ÷ 5
```

모듈 효율 20% 기준 1 kWp 당 약 5 m² 다. **밀도 하나가 GCR 과 경사각을 함께**
정한다 — 고밀도 배치는 이격을 좁히는 대신 경사를 낮춰 음영을 줄이는 실무
관행이다.

| 밀도 | GCR | 경사 | 1,000 m² | 상충 |
|---|---|---|---|---|
| 높음 | 0.55 | 15° | 110 kWp | 면적당 용량 최대, kWp당 발전량 최소 |
| 보통 | 0.40 | 25° | 80 kWp | 균형점 (기본값) |
| 낮음 | 0.30 | 30° | 60 kWp | kWp당 발전량 최대, 용량 최소 |

**용량 곡선은 시뮬레이션 1회 + 곱셈이다.** pvwatts 직류와 인버터 모델이 정격에
선형이다(정격과 인버터 용량이 함께 커진다). 20단계라도 태양 위치 계산은 한 번이며
선형성을 시험이 고정한다. 되풀이한다면 20단계 × 감도 3 = 60회가 되어 그것이
최대 병목이 된다 — 실측으로 확인했다 ([6.4](#tech-performance)).

**일몰 후 발전량을 태양 고도로 잘라낸다.** 시간별 → 15분 선형 보간이 일몰을
가로질러 값을 흘리기 때문이다.

**방위는 8방위로 받는다** (15세션). 45도 간격이면 최대 오차 22.5도이고 발전량
차이가 1–2% 라 예측 오차 안에 묻힌다. 선택지 라벨에 상대 발전량을 병기하는데
**하드코딩하지 않는다** — 고른 지역·경사각으로 여덟 방위를 각각 돌려 남향 대비
비율을 낸다. 경사가 낮으면 방위 영향이 줄기 때문이다.

| 경사 | 남 | 남동 | 남서 | 동 | 서 | 북 |
|---|---|---|---|---|---|---|
| 25° (밀도 보통) | 기준 | −8% | −1% | −20% | −10% | −31% |
| 15° (밀도 높음) | 기준 | −5% | −1% | −13% | −7% | −19% |
| 90° (벽면) | 기준 | −18% | −1% | −40% | −21% | −64% |

시뮬레이션 여덟 번이라 0.85초다. 용량을 1 kWp 로 고정하므로 **면적·밀도를 바꿔도
비율이 같고**, 캐시가 지역·경사·손실로 걸린다.

**벽면 어레이를 함께 올릴 수 있다.** 지붕과 방위를 따로 고르고 경사 90°·GCR 1.0
으로 계산한다. 단위 프로파일은 두 어레이를 합쳐 총용량으로 나눈 값이라 섞인 방위가
그대로 반영된다 (`PvSystemConfig.scaled()` 이 비율을 유지한다).

**용량은 한 줄로 판정한다** (15세션 1-3). 20단계를 훑는 것은 그대로지만 표를
화면에 나열하지 않는다.

    회수기간이 있으면  그 최소점
    없으면(단가 미입력) 절감액(역률 악화분을 뺀 값) 최대점

**새 산식을 만들지 않는다** — 이미 훑은 점에서 고르기만 한다
(`SolarCurve.verdict()`). 무엇이 최적을 멈춰 세웠는지(면적 상한 / 잉여 발생 /
기본요금 절감 포화)를 판별해 화면에 한 줄 적는다. 화면에는 대표 다섯 지점을
표로 내고 곡선은 접어 둔다. 20단계 상세는 Excel 「태양광 용량 곡선」 시트로 간다.

**회수기간이 평평하면 최소점을 그냥 고르지 않는다** (16세션 0-4). kWp당 단가면
투자비도 절감액도 용량에 비례해 회수기간이 용량과 거의 무관해진다 — 실측에서
8 kWp 가 8.060년, 상한 160 kWp 가 8.114년이었다. 최소점을 그대로 고르면 상한의
1/20 이 답이 된다. 0.7% 차이는 발전량 예측 오차(R² 0.8) 안이므로, 최소
회수기간의 `pv.payback_tie_ratio` 안에 드는 점 가운데 절감액이 큰 것을 고른다.
잉여로 회수기간이 실제로 꺾이면 꺾인 뒤 점들이 이 폭을 벗어나 최소점이 남는다.

**참고단가를 제공하지 않는다.** ESS 는 에너지경제연구원 LCOS 연구를 인용할 수
있지만 태양광은 확보하지 못했다. 단가를 넣지 않으면 투자비는 **0원이 아니라
미산출**이고 사유가 붙는다. 0원으로 두면 회수기간이 0년으로 나와 "즉시 회수"로
읽힌다. 용량 곡선의 모든 점에 같은 kWp당 단가를 적용하므로 **규모의 경제가
반영되지 않는다** — 소규모 구간의 회수기간이 낙관적으로 나온다.

#### 7.6 ESS {#tech-ess}

목표 요금적용전력에서 출력·용량·방전시간을 역산한다.

**목표를 사용자가 찍게 두지 않는다** (14세션에 바꿨다). 피크의 90%에서는 용량이
4,094 kWh 로 사례 범위를 훌쩍 넘고, 조금만 올리면 방전시간이 0.44시간까지 줄어
고출력 셀이 된다. 그 사이 어딘가에 최적점이 있으므로 **훑어서 찾는다.**

    필요 출력 = 초과분 최대값 (kW)
    필요 용량 = 하루치 초과 에너지 합의 연중 최대값 (kWh)
    과금 용량 = max(필요 용량, 시장 최소 100 kWh)
    투자비   = 고정비 + 용량단가 × 과금 용량 + 전기공사
    절감액   = 저감량(kW) × 기본요금단가 × 12       ← **현행 요금제** 기준
    회수기간 = 투자비 ÷ 절감액

**기본요금단가는 현행 요금제 기준이다.** 최적 요금제로 바꾼 뒤의 단가를 쓰면 ESS
절감액이 선택요금 전환에 딸려 움직여 2단계 독립 평가가 깨진다.

**격자를 10 kW 이하로 둔다.** 곡선이 격자에 민감하다 — 50 kW 간격이면 5,150 kW
26.7년에서 멈추고, 10 kW 간격이라야 5,170 kW 24.6년을 찾는다.

**회수기간 곡선은 U자다.** 왼쪽은 최소 규모 100 kWh 를 다 못 쓰는 구간이고,
오른쪽은 용량이 급증해 투자비가 늘어나는 구간이다. **물리적 최적이 아니라 조달
규격의 산물이다.** 화면은 곡선에 최소 지점 표식을 찍고 대표 지점 대여섯 개를 표로
낸다. **목표 슬라이더는 없다.**

| 목표 | 저감 | 필요 용량 | 과금 용량 | 투자비 | 회수기간 |
|---|---|---|---|---|---|
| 5,200 kW | 93 kW | 35 kWh | 100 kWh | 2.62억 | 32.3년 |
| 5,180 kW | 113 kW | 72 kWh | 100 kWh | 2.62억 | 26.6년 |
| **5,170 kW** | **123 kW** | **101 kWh** | **101 kWh** | **2.63억** | **24.6년** |
| 5,150 kW | 143 kW | 183 kWh | 183 kWh | 3.31억 | 26.7년 |
| 5,100 kW | 193 kW | 432 kWh | 432 kWh | 6.11억 | 36.4년 |

**용량 산정 기준은 '하루 최대 초과 에너지'다.** 충전 기회가 야간뿐이므로
연속 구간 최대로 잡으면 같은 날 초과가 두 번일 때 목표를 놓친다(샘플
5,200 kW 에서 실제로 놓쳤다). 기간 합계인 '총 초과 에너지'는 배터리 용량으로는
과대다(4,500 kW 목표에서 178 MWh).

**투자비는 조달 사례 회귀로 낸다** (13세션에 교체했다).

    설비비 = 106,925,000원 + 840,000원/kWh × 용량(kWh)   R² 0.99958 (옥외 관급 4건)
    투자비 = 설비비 + 전기공사비

계수는 `data/ess_cost_model.json` 에 있고 `tools/fit_ess_cost.py` 가 다시 맞춘다.
**코드에 손으로 적지 않는다.** 홀드아웃(한 건씩 빼고 예측) 오차는 1.0~2.5% 다.
계수는 **천 원 단위로 반올림**해 저장한다 (14세션) — 사례가 넷이라 그 아래 자리는
뜻이 없고, 반올림 재현 오차는 −0.85~+1.43% 로 사실상 달라지지 않는다.

**단가 입력은 2계수 방식이다** (14세션). kW당 단가로는 표현할 수 없다 — 같은
100 kW 인데 용량이 156.4 kWh 면 2.35억, 400 kWh 면 4.43억이다. 확장 패널에서
**고정비와 용량단가 둘만** 조정하고, 조정하면 「계수 조정됨」을 표시한다.
견적 총액 직접 입력 경로는 그대로 둔다.

- **단일 kWh당 단가로 표현하지 않는다.** 고정비가 1.07억으로 지배적이라
  총액÷용량이 50 kWh 440만원, 400 kWh 146만원으로 세 배 변한다.
- **kW 는 설명 변수가 아니다.** PCS 가 50·75·100 kW 로 흩어져 있는데도 kWh
  하나로 R² 가 0.999 를 넘는다.
- 전기공사는 옥외 기준 200 kWh 이하 6,300만~8,300만원, 400 kWh 약 1.41억원이다.
  실내 설치면 줄지만 근거가 한 건뿐이라 참고값이다.
- 적용 구간은 100~400 kWh 다. 아래는 100 kWh 로 올려 산정하고 알리며, 위는
  참고값으로 표시한다.

**핵심 산출물은 성립 조건이다.** 회수기간 하나로는 "왜 안 되는가" 를 알 수 없다.

    kW당 배터리비 = 용량단가 × 방전시간
    10년 절감/kW  = 기본요금단가 × 12 × 10
    마진/kW       = 절감 − 배터리비
    필요 저감량   = (설비 고정비 + 전기공사) ÷ 마진

기본요금 단가는 계약종별·전압·선택요금에서 가져온다. 샘플(목표 5,200 kW, 방전
0.44시간)에서는 필요 저감량 358 kW, 산출된 저감량 93 kW 다.

**판정 문장을 쓰지 않는다** (14세션). 「성립하지 않습니다」·「경제성 없음」 같은
단정 대신 두 값을 나란히 놓고 사실만 적는다 — 곡선이 근거이므로 판단은 사용자가
한다. LCOS 참고단가는 차익거래 에너지 단가와 2030년 전망 회수기간에만 남겼다.

차익거래 수익은 매 평일 한 사이클을 온전히 돌렸을 때의 잠재값이며 피크저감
절감액에 **합산하지 않는다** — 피크컷 디스패치가 이미 일부를 실현하고 있어
합산하면 이중 계산이다.

#### 7.7 잉여 활용 {#tech-surplus}

상계거래 금액은 그 슬롯의 계절·시간대 단가로 상계되므로 데이터에서 나온다.
잉여 판매는 단가가 없으면 산출하지 않는다 — **우리가 파는 쪽이다.**
**자격요건은 판정하지 않는다.** 잉여가 0 이면 그 사실만 적는다 — **카드를
비활성으로 만들지 않는다** (14세션 2-3).

### 4.4 조합 재계산 — 왜 단순 합이 아닌가 {#tech-combination}

**수단별 절감액을 더하면 틀린다.** 수단이 서로의 전제를 바꾸기 때문이다.

| 상호작용 | 무슨 일이 일어나나 |
|---|---|
| 요금제 → 다른 수단 | 기준 단가가 바뀌어 계약전력·역률·ESS 절감액이 달라진다 |
| 태양광 → 선택요금 | 사용량이 줄면 **최적 선택요금이 바뀐다.** 기본요금 비중이 커지므로 |
| 태양광 → 역률 | 유효전력이 줄어 역률이 나빠진다. 기본요금에 추가가 붙는다 |
| ESS → 기본요금 | 피크를 낮추면 기본요금 기반 자체가 달라진다 |
| 태양광·ESS → 역률 감액 | 역률 감액은 기본요금에 비례한다. 기본요금이 줄면 감액도 준다 |
| 계약전력 → 하한 | 계약전력을 낮추면 요금적용전력 하한이 함께 내려간다 |

그래서 조합마다 **부하를 처음부터 다시 만들어** 요금을 한 번 계산한다.

```
부하 → apply_generation(PV) → dispatch_peak_shaving(ESS) → calculate_bill()
```

**역률도 조합에 넣는다** (14세션). 역률은 부하를 바꾸지 않고 기본요금 조정액만
바꾸므로 `BillingOptions.power_factor_pct` 로 얹는다. 넣지 않으면 위 표의 다섯째
줄(기본요금이 줄면 역률 감액도 준다)이 보이지 않는다.

**3단계는 세 부분이다** (14세션 5절).

| 부분 | 무엇을 | 어디서 |
|---|---|---|
| ① 개선안별 요약 | 독립 평가 결과 **그대로**. 재계산 금지 | `report.standalone` |
| ② 합산효과 | 조합 재계산 + **단순 합과의 차이** | `compare.combination` |
| ③ 조합 비교 | 조합을 쌓아 올려 견준다 | `compare.combination` |

②의 **차이**가 3단계의 존재 이유다. 차이가 생긴 이유는 위 표에서 **실제로 발생한
것만** 골라 적는다 — 해당 없는 줄을 적으면 없는 상호작용을 만들어낸다.

**계약전력 추가 하향 여지는 ②에서만 낸다.** 2단계 7.2 카드는 현재 부하 기준이라
다른 수단을 켜도 값이 바뀌지 않는다 (독립 평가). 조합 부하 기준의 여지는
`evaluate_contract_adjustment(usage, combined.bill, ...)` 로 따로 계산한다.

**경제성DR·잉여 활용은 ②에 넣지 않는다.** 요금이 아니라 별도 정산·수익이라 조합
부하에 얹을 수 없다. ①에는 그대로 있고, ②는 그 사실을 적는다 — 같은 것을 비교
하지 않으면 「차이」가 뜻을 잃는다.

**조합 확실성은 가장 낮은 구성 요소를 따른다.** 태양광과 ESS 를 함께 넣으면
조합 전체가 ESS 등급이다. 표에서 등급을 섞어 보여주면 의사결정이 흐려진다.

**켠 수단만 조합에 들어간다.** 켜지 않은 수단이 섞이면 "보지 않은 것"이
"검토했더니 이만큼"으로 둔갑한다. 반대로 조용히 빼면 "효과가 없었다"로 읽히므로
「검토 범위」로 명시한다.

### 4.5 감도 — `sharpen()` {#tech-sensitivity}

발전량 예측은 **총량은 실측과 부합하나 피크 발전량을 과소 산출하는 경향**이
있다 (재분석 데이터의 평탄화 편향). 그래서 흔드는 축은 총량이 아니라
**정오의 첨예도**다.

```
adjusted(t) = 일평균발전 + (기준(t) − 일평균발전) × s
```

**일별 총량이 보존된다.** 발전이 있는 슬롯만의 일평균을 쓴다 — 야간 0 을
넣으면 밤의 편차가 전체를 지배한다. `s = 1.0` 이면 **원본을 그대로 돌려준다**
(부동소수 오차조차 만들지 않는다). 기준 시나리오가 시뮬레이션 결과와 완전히
같아야 회귀값이 흔들리지 않는다.

`sharpen` 은 양의 상수배에 **동차**이므로 단위 프로파일에 한 번 걸고 용량을
곱한 것과 용량을 곱한 뒤 조정한 것이 같다. 20단계마다 다시 계산할 이유가 없다.

| 시나리오 | s | 뜻 |
|---|---|---|
| 평탄형 | 0.85 | 정오가 덜 뾰족하고 어깨가 두껍다 |
| 기준 | 1.00 | 시뮬레이션 그대로 |
| 첨예형 | 1.25 | 정오가 뾰족하고 어깨가 얇다 |

#### 상한이 고정되지 않는 이유 {#tech-sensitivity-range}

**'첨예형'은 좋은 값이 아니다.** 총량이 보존되므로 첨예도를 올리면 정오가
높아지는 대신 **아침·저녁 어깨가 낮아지는데, 피크 저감은 어깨 출력에 걸린다.**
부하 피크가 정오에 정확히 있지 않으면 첨예형이 오히려 불리하다.

케이스 스터디 6종 × 3용량 = **18개 조합에서 기본요금 절감액의 상한 시나리오는
평탄형 16건, 기준 2건, 첨예형 0건**이었다.

그래서 결과를 **범위로 표시한다.**

```
기본요금 절감  3,152만원 (프로파일 감도 범위 2,897 ~ 3,266만원)
```

세 값을 나란히 놓으면 읽는 사람이 "어느 쪽이 좋은 값인가"를 찾게 되는데 이
축에는 좋고 나쁨이 없다. 최댓값·최솟값은 `min`/`max` 로 뽑고 **어느 시나리오가
상한인지 고정하지 않는다.** 원자료 3행은 근거표로 별도 시트에 둔다.

**요금제 전환·계약전력 조정·역률 개선에는 감도를 적용하지 않는다** — 실측
데이터와 요금표·약관만으로 확정되는 계산이다. 확률 표기(P90 등)는 쓰지 않는다.
부하가 1년 실측 고정이라 통계적으로 부정확하다.

### 4.6 안내 체계 — 등급 넷과 사실 ID {#tech-notices}

**같은 문구를 두 번 내지 않고, 화면에서 뺀 것은 반드시 산출물에 있다.**

안내는 :class:`Notice` 하나다. 문구를 만드는 **발신처가 등급과 사실 ID 를 함께
붙인다** — 받는 쪽이 문구를 훑어 짐작하지 않는다.

| 등급 | 뜻 | 화면 | 보고서 |
|---|---|---|---|
| 차단(BLOCK) | 계산이 안 됨 | 본문 · 색 | 본문 |
| 주의(WARN) | 결과 해석이 달라짐 | 본문 · 아이콘 | 본문 |
| 근거(BASIS) | 이 숫자가 어디서 왔나 | **툴팁** | 본문 · 부록 A |
| 참고(INFO) | 전제·한계·제도 | **없음** | 부록 C |

**사실 ID 가 중복을 가른다** (`모듈.사실`, 여럿이면 `모듈.사실:판별자`).
문구가 아니라 ID 로 견주므로 두 모듈이 같은 사실을 조금 다르게 적어도 한 번만
나간다. 같은 사실이 여러 벌일 때(월별 결측률·정전 구간·조합)는 판별자로 가른다.

```
ess.charge_new_peak            measures\ess.py 와 compare\combination.py 가 함께 쓴다
quality.month_missing_rate:2023-11   달이 판별자다
```

**앞말은 표시할 때만 붙인다** (`prefixed`). 조합명을 문구에 심으면 그 앞말이
중복 판정에 걸려 같은 조합의 다른 경고가 통째로 사라진다.

18세션까지 쓰던 **부분 문자열 등급 추정은 21세션에 지웠다.** ``fact`` 는 필수라
빠뜨리면 mypy 가 잡는다. `tools\notice_audit.py` 가 실주행으로 한 번 더 센다.

### 4.7 계산 근거 — 산식과 대입값 {#tech-worksheet}

카드마다 **접힌 「계산 근거」** 가 있다. 산식과 그 자리에 넣은 값을 같은 줄에
둔 표 하나다 (`kwise.report.worksheet`).

```
기본요금   5,293.4 kW × 8,320 원/kW × 12.00개월   521,823,000원
전력량요금  계절·시간대별 단가 × 사용량
  경부하                              8,871,534 kWh
  소계                              2,775,718,000원
합계                                3,297,542,000원
```

**LaTeX 을 쓰지 않는다.** 화면(Streamlit)·Excel·Word 셋이 같은 표를 써야 하므로
구분·산식·값 세 열로 낸다. 만드는 함수가 하나이므로 세 산출물이 갈라질 수 없다.

**여기서 다시 계산하지 않는다.** 이미 나온 결과 객체의 값을 배치할 뿐이다 —
산식을 다시 적으면 화면의 숫자와 근거의 숫자가 갈라진다.

**화면 예산.** 카드·절마다 본문 3줄 · 확인사항 3항목이 한도다 (값은
`assumptions.json` 의 `ui.body_line_budget`·`ui.notice_budget`). 접힘과 툴팁은
한도 밖이다 — 펼치지 않아도 눈에 들어오는 글만 센다.
``tools\screen_budget.py`` 와 시험이 **같은 함수**로 잰다.

### 4.8 예외 처리 기준 {#tech-exceptions}

**"모르는 것을 모른다고 표시한다"가 이 절의 전부다.**

| 상황 | 처리 | 하지 않는 것 |
|---|---|---|
| **결측** | 미보간. 계산에서 제외하고 결측률을 표시. 5% 초과 월은 관측·보정 두 기준 병기 | 보간, 0 채우기 |
| **정전** | 흔적 3종 중 **연속 결측을 뺀 나머지 2개 이상**이면 정전. 편중 판정에서 분자·분모 양쪽에서 제외 | 연속 결측만으로 정전 판정 |
| **그리드 이탈 행** | kW 산정에서 제외, **kWh 합계에는 포함**. 수단을 적용해도 건드리지 않는다 | 평균 환산 (43.2 kWh ÷ 14분 = 185 kW 로 왜곡된다) |
| **단가 미입력** | 투자비 `None` + **사유**. 회수기간도 미산출 | 0원 (→ "즉시 회수"로 읽힌다) |
| **하한 규정 미확인** | 하향 여지(kW)만 내고 금액은 미산출 | 30% 가정 |
| **기상 취득 실패** | 캐시 → API → 사전 취득분 순, 셋 다 없으면 **중단하고 안내** | 인접 격자 대체, 0 으로 계산 |
| **갑 종별 계약전력 없음** | 예외를 던져 멈춘다 | 요금적용전력으로 대체 |
| **기준 데이터 파일 손상** | 최근 백업 → 출고값 순 복구 후 **반드시 알린다** (`recovered_from`) | 조용한 복구 |
| **기준 데이터 없음** | `RuleDataError` 로 멈춘다 | 코드 기본값 사용 |

**정전 판정에서 연속 결측을 흔적으로 세지 않는 이유.** 연속 결측은 모든
결측이 갖는 성질이라 정전의 근거가 못 된다. 이 조건 덕분에 샘플의 11월 통신
장애(930슬롯, 9.69일)가 정전으로 오인되지 않는다.

**최장 연속 결측을 편중 배수와 별도로 낸다.** 며칠짜리 공백은 시간대가 균등하게
빠져 배수가 1 근처가 되지만, 그 달의 최대수요 판정 자체를 무의미하게 만든다.

### 4.9 외부 인터페이스 — Open-Meteo {#tech-weather}

기상은 **Open-Meteo Archive API** (ERA5 재분석) 하나뿐이다. CC BY 4.0.

| 항목 | 값 |
|---|---|
| 변수 | `shortwave_radiation` `direct_normal_irradiance` `diffuse_radiation` `temperature_2m` `wind_speed_10m` |
| 해상도 | 시간별. ERA5 격자 25~31 km |
| 캐시 키 | **0.25° 격자로 반올림.** 시군구든 좌표 입력이든 같은 격자면 공유 |
| 재시도 | 429·5xx·연결 실패에 지수 백오프 (최대 5회, 2초 → 120초) |
| 호출 간격 | 최소 1초 (`Pacer`). 429 를 맞고 백오프하는 것보다 빠르다 |
| 폴백 | Windows PowerShell 경유. 프록시 뒤에서 Python HTTPS 만 막히는 사례가 있다 |

**조회 순서를 바꾸지 않는다.**

```
① PROJECT_CACHE 캐시   반복 호출을 여기서 막는다
② Open-Meteo API       성공분은 ①에 캐시한다
③ 사전 취득분          **폴백했다는 사실을 결과에 표시한다**
④ 둘 다 없으면 중단    0 으로 계산하거나 인접 격자로 대체하지 않는다
```

**시군구 단위 선택으로 충분하다.** ERA5 격자가 25~31 km 인데 서울 25개 구의
좌표 폭이 남북 20.6 · 동서 29.0 km 다. 같은 셀을 조회하므로 정확도를
희생하지 않는다. 좌표 직접 입력은 산악·해안 지형용 옵션으로 남긴다.

**Open-Meteo 라벨 규약은 미확정이다.** 라벨이 구간 시작이라는 전제로 대표
순시각을 라벨 + 30분으로 두었다. 실측 발전 데이터를 얻으면 발전 곡선이 통째로
30분 밀렸는지 대조한다. `WeatherLabel` 로 바꿔 끼울 수 있다.

## 5. 기준 데이터와 갱신 {#tech-rules}

### 5.1 데이터 목록과 출처 {#tech-rules-list}

법령 유래 수치가 코드 상수로 흩어져 있으면 사람이 볼 수도 고칠 수도 없다.
근거와 확인일을 붙여 파일로 옮겼다.

| 파일 | 항목 | 근거 |
|---|---|---|
| `rules_kr.json` | **27개** | 조문 (약관 제41·42·43·56·57·58·68조, 운영규칙 제12장) |
| `assumptions.json` | **25개** | `"판단값"` |

**섞지 않는다.** 섞으면 "이 숫자를 우리가 정한 것인가 법이 정한 것인가"를
되물을 수 없는데, 그 물음이 갱신 판단의 전부다. **스키마가 이를 강제한다** —
법령 유래 항목에 근거 조문이 비면 파일 읽기가 거부된다.

담긴 것: 역률 9개 · 요금적용전력 4개 · 계약종별 임계 3개 · DR 3개 ·
계절·시간대·요일 5개 · 판단값 25개(감도 s · PV 밀도 · DR 분위수 · ESS 효율 ·
만료 임계 · 진행률 가중치 등).

#### 모듈 상수로 붙잡지 않는다 {#tech-rules-lookup}

**이것이 이 절에서 가장 중요하다.** 값을 파일로 옮기고도

```python
LAGGING_STANDARD_PCT = 92.0  # ← import 시점에 고정된다
```

처럼 붙잡아 두면 **화면으로 파일을 고쳐도 그 프로세스에서는 옛 값으로
계산된다.** 코드에 기본값을 남기는 것과 같은 사고이고, 값이 그럴듯해서 결과를
다 쓰고 나서야 발견된다. 전부 함수 조회로 바꿨다.

```python
def lagging_standard_pct() -> float:
    return float(rule_value("power_factor.lagging_standard_pct"))
```

**데이터클래스 필드 기본값도 같다.** `field(default_factory=...)` 라야 생성
시점에 읽는다. 그냥 기본값으로 두면 import 시점에 고정된다.

### 5.2 갱신 절차 {#tech-rules-update}

무엇을 언제 갱신하는지, 어떻게 고치는지는 **매뉴얼 7장**에 있다. 여기서는
설계 근거만 적는다.

**편집 방식을 데이터 성격에 따라 나눴다.**

| 방식 | 대상 | 이유 |
|---|---|---|
| 엑셀 왕복 | 요금 단가, 시군구 좌표 | 항목이 많고 표 구조다 |
| **화면 편집** | 기준 데이터 | 항목이 적고 **근거가 함께 보여야** 한다 |

되읽기는 **항목 키를 대조해** 행이 빠지거나 키가 바뀌면 거부한다. 조용히
항목이 사라지면 코드에 기본값이 없으므로 다음 실행이 멈추고 원인을 찾기 어렵다.

`set_value`·`confirm` 은 **순서를 지킨다.**

```
① 검증 → 실패하면 저장하지 않고 어느 항목이 왜 틀렸는지 돌려준다
② 편집 직전 상태를 backup\ 에 남긴다 (최근 10개)
③ rules_history.jsonl 에 한 줄 남긴다
④ 캐시를 비운다
```

**④가 없으면 파일은 바뀌었는데 계산은 옛 값으로 돈다.** 화면 쪽 캐시는 두
겹으로 막는다 — 편집 훅이 `st.cache_data.clear()` 를 부르고, 모든 캐시 키에
기준 데이터 지문을 물린다. 훅만 두면 엑셀 왕복·손편집을 놓치고, 지문만 두면
지문을 빠뜨린 캐시가 조용히 샌다.

**요금표는 엑셀 변환이고 수기 입력은 금지다.** 60개 값을 손으로 옮기면 오차가
섞인다 — 실제로 엑셀의 농사용(을) 단가가 원본과 다르다(66.6 vs 68.6원).
계절 열은 **헤더 이름**으로 매핑한다. 산업용 시트만 봄·가을이 여름보다 앞이라
위치로 읽으면 태양광 평가가 정반대가 된다. **검증 실패 시 파일을 쓰지 않는다.**

**자동 수집은 하지 않는다.** 한전 요금표는 API 가 없고 연 1~2회 개정이라 수동
갱신이 현실적이다. 자동화하면 원문이 바뀐 것을 알아채지 못한 채 파싱만
실패하고 **그 실패는 조용하다.** 대신 만료 경고에 원문 확인처를 함께 싣는다.

만료 임계는 요금 단가 12개월 / 약관·규칙 24개월 / 참고단가 24개월 / 기상은
전년도 미확보 시다. **임계값도 `assumptions.json` 에 있다** — 코드에 두면
"왜 12개월인가"를 물을 곳이 없다.

### 5.3 원복과 이력 {#tech-rules-restore}

```
data\defaults\   출고 기본값. 커밋. 읽기 전용
data\            현재 값
data\backup\     편집 직전 스냅샷 (최근 10개, .gitignore)
```

| 원복 | 규약 |
|---|---|
| ① 직전 상태 | **되돌리기 자체도 백업한다** — 되돌린 것을 되돌릴 수 있어야 한다 |
| ② 출고 상태 | **확인 전에는 실행하지 않고** 달라지는 항목만 돌려준다 (`confirmed=False`) |
| ③ 항목별 | 한 항목만. 나머지는 건드리지 않는다. 실무에서 가장 많이 쓰인다 |

**여기서 버그를 둘 잡았다.**

1. **직전 복원이 방금 만든 상태를 되돌렸다.** 안전 백업을 쓰면 그것이 목록 맨
   앞으로 올라오는데 복원 함수가 목록을 다시 읽어 그 안전 백업을 복원했다.
   되돌릴 대상을 **미리 잡아 두는** 것으로 고쳤다.
2. **같은 분에 두 번 백업하면 앞엣것을 덮어썼다.** 파일명이 분 단위라 편집
   백업과 안전 백업이 같은 이름이 되어 편집 **직전** 상태가 사라졌다.

둘 다 시험이 없었으면 실사용에서, 그것도 "되돌렸는데 안 돌아간다"는 형태로
드러났을 것이다.

### 6.4 성능 {#tech-performance}

`tools\run_benchmark.py` 가 잰다. **구간별 소요 · RSS 증감 · `calculate_bill`

**요금 재계산은 곱해지지 않는다.** 곡선 21회(=단계+1), 조합 4회(=조합 수),
감도 3회(=시나리오 수). 시험 둘이 이 숫자를 못 박는다.

#### 최적화 이력 — Period 박싱 제거 {#tech-optimization}

물음은 "PV 발전량을 20단계 × 감도 3 = 60회 다시 계산하는가"였고 **답은
아니오**였다. 시뮬레이션은 1회, 용량은 곱셈이다.

되풀이되던 것은 **발전량이 아니라 요금**이었다. 프로파일러가 찍은 자리는
`calculate_bill` 시간의 **74%를 먹던 `PeriodArray._box_func` 180만 회**였다.

```python
for month in months:  # 13개월
    month_mask = slots["month"].to_numpy() == month  # 3만 5천 개를 매달 상자에
```

`slots["month"]` 는 Period 열이라 `to_numpy()` 가 그때마다 전 슬롯을 파이썬
`Period` 객체로 상자에 넣는다. 루프 밖으로 한 번만 끌어올렸다.

| | 전 | 후 |
|---|---|---|
| `calculate_bill` 1회 | 0.63초 | **0.145초** (4.3배) |
| 파이프라인 전체 | 24.6초 | **9.4초** (2.6배) |
| 케이스 스터디 6종 | 114.2초 | **29.9초** (3.8배) |
| pytest 전체 | 324초 | **98초** (3.3배) |

**회귀값은 한 자리도 바뀌지 않았고** 케이스 스터디 66/66 그대로다.

**교훈.** 시간만 봤으면 "곡선이 느리다"에서 멈췄다. 호출 수를 함께 세었기에
발전량이 아니라 요금이 곱해진다는 것을 먼저 알았고, 프로파일러가 그 안의
진짜 자리를 찍었다.

#### 메모리 측정 {#tech-memory}

Windows 작업 집합을 `GetProcessMemoryInfo` 로 직접 읽는다. `tracemalloc` 은
파이썬 할당자만 보므로 **NumPy 배열이 빠지는데**, 이 도구에서 메모리를 쥐는
것이 바로 그 배열이다.

> `ctypes` 호출에서 `argtypes` 를 지정하지 않아 64비트에서 핸들이 잘렸고,
> 호출이 **조용히 실패해 0 이 돌아왔다.** 표에 "0 MB"로 찍혀 있었다 — 못 잰
> 것을 안 썼다고 읽을 뻔했다. 지금은 못 재면 `None` 이고 표에 `—` 로 나온다.

#### Streamlit Cloud 대비 {#tech-cloud}

| 항목 | 실측 | 판단 |
|---|---|---|
| 최대 RSS | 273 MB | 한도 1 GB 의 **27%** |
| 최대 구간 | Excel 쓰기 +45.8 MB | 15분 시계열 시트. 체크박스로 끌 수 있다 |
| 업로드 | 3년치 **2.5 MB** | 기본 상한 200 MB — 79배 여유 |
| 얕은 클론 | 23 MB (weather 20 MB) | pip 설치 수백 MB 에 비하면 무시할 수준 |

**동시 사용.** `st.cache_data` 는 프로세스 전역이라 접속자가 캐시를 공유한다.
키가 요약 정보(파일명·기간·총량)뿐이면 다른 파일이 같은 키를 가질 여지가 남고
그때 옆 사람 결과가 나온다 — **업로드 바이트의 내용 해시**를 키에 물렸다.
가장 무거운 셋(태양광 곡선·조합 비교·감도)은 세션 기억으로 옮겨 세션 밖으로
나가지 않는다.

**임시 파일.** 업로드 바이트는 메모리에만 있다. 산출물은 세션별 uuid 폴더에
만들었다가 **바이트로 읽은 즉시 지운다.** 앱을 켤 때 묵은 폴더(6시간)를
쓸어내는 그물을 함께 둔다.

무효전력 계량 계기를 설치한다"는 취지의 서술을 찾았다. 사실이라면 고압 갑

손으로 옮겨 적다 틀린 전례가 있고, 근거 없이 그럴듯한 값이 들어가는 것이 이
프로젝트가 가장 경계하는 사고다.

## 부록 A. 요금 데이터 스키마 {#부록-a-요금-데이터-스키마}

전체 스키마는 요구사항서 부록 A 에 있다. 여기서는 **검증 규칙과 확장 시
주의점**만 적는다.

| 규칙 | 내용 | 적용 범위 |
|---|---|---|
| 1 | 시간대 단가 `경 < 중간 < 최대` | `time_of_use=true` 종별만 |
| 2 | 선택요금 간 균일성 | 선택Ⅲ 미적용 (할인이 최대부하에 집중된 설계다) |
| 3 | 기본요금 단가 양수 | 전부 |
| 4 | 계절 3종이 모두 있을 것 | 전부 |

**전체시간 종별**(갑Ⅰ·교육용(갑))은 세 시간대에 같은 단가 + `time_of_use=false` 다.
스키마를 갈라 두면 엔진이 두 갈래가 되므로 **검증만 갈랐다.**

**검증 정책은 코드에 둔다** (`validate.DEFAULT_POLICY`). 요금 단가가 아니라
데이터에 대한 우리의 기대이고, 요금표를 갱신했다고 검증기가 먼저 깨져서는
안 된다.

**단가를 임의로 고치지 않는다.** 검증 실패는 경고로 남기고 규칙 쪽을 검토한다.
고치면 요금표 조작이 된다.
